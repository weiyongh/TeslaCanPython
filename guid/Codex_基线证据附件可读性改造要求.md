# Codex 基线证据附件可读性改造要求

## 1. 本次修改目标

目前 `采集时间线与关键Signal.md` 与 `DBC关键Signal覆盖与可读性.md`
的数据提取和工程追溯已经足够，但人读层仍偏向"程序数据表"。

本次**只修改两个 Markdown 附件的呈现层**，不修改：

-   ASC 原始数据；
-   DBC 选择与定义；
-   Signal 解码结果；
-   事件识别逻辑；
-   原始采样时间；
-   CSV 追溯文件；
-   工程审计结果。

目标不是减少后台数据，而是让人能够快速回答两个问题：

1.  **采集过程中什么时候发生了什么，控制链关键 Signal 当时分别是多少？**
2.  **本实验到底使用了哪些关键
    Signal，它们代表什么、是否可用、在控制树中承担什么角色？**

总体原则：

> **后台保留完整数据，前台只呈现诊断所需信息。**

> **时间线按时间读，Signal 表按控制关系读。**

# 2. `采集时间线与关键Signal.md` 改造要求

## 2.1 第一列必须是时间，不使用 E01/E02 作为人读索引

当前 `E01、E02……` 可以继续作为程序内部事件 ID，保存在 CSV、JSON
或工程审计中，但不要作为人读 Markdown 主表的第一列。

主表第一列统一为：

**`时间(s)`**

时间使用 ASC 相对时间秒。

原因：人回看一次实车采集时，最自然的定位方式是"第几秒发生了什么"，而不是先记住
E34 再去其他表寻找 E34。

------------------------------------------------------------------------

## 2.2 不再把同一事件拆成三张大表

当前结构将同一批事件分别放入：

-   实际时间线；
-   控制与动力关键值；
-   能源与制动关键值。

这种结构方便程序组织，但不方便人阅读。

改为：

> **一张"关键采集时间线"主表 + 必要的专项小表。**

主时间线应把同一时刻最重要的信息横向放在一行。

------------------------------------------------------------------------

## 2.3 主时间线固定列顺序

建议固定为：

  -----------------------------------------------------------------------------------------------------------------------------
    时间(s) 状态/动作     电门(%)   请求扭矩(Nm)   实际扭矩(Nm)   车速(km/h)   电驱功率(kW)   Pack电流(A)   Pack功率(kW) 备注
  --------- ----------- --------- -------------- -------------- ------------ -------------- ------------- -------------- ------

  -----------------------------------------------------------------------------------------------------------------------------

列顺序必须体现人的诊断阅读逻辑：

**时间 → 发生了什么 → 驾驶输入 → 控制请求 → 执行反馈 → 车辆运动 →
能源响应 → 解释**

不要按照 CAN ID、Message、程序对象或数据源排序。

### 关于其他 Signal

-   挡位、系统状态：只有对该节点有意义时，写入"状态/动作"或"备注"。
-   轴速：如果本实验需要，可以保留；若车速已经足够表达运动结果，不要求每份附件永久占一列。
-   Pack
    电压：属于重要车型基线数据，但在一次短时间加速的主时间线中变化很小，可放在关键节点表、摘要或专项表中，不必为了完整性挤占每一行。
-   制动输入/制动状态：只在制动相关工况中重点展示，不让整个加速时间线长期携带大量制动字段。

------------------------------------------------------------------------

## 2.4 主时间线只保留有诊断意义的关键节点

当前程序识别出的全部事件继续保存，但**人读主表不要机械输出全部事件**。

优先保留：

-   初始状态；
-   挂 D；
-   零电门正驱动/低速运动建立；
-   开始踩电门；
-   加速早期代表点；
-   请求/实际扭矩关键峰值；
-   高负载能源输出关键点；
-   首次达到目标车速；
-   请求转负/回收建立；
-   电门归零；
-   制动；
-   近零车速；
-   回 P；
-   第二轮对应关键节点；
-   特殊工况真正有分析意义的节点。

相距很近、属于同一物理过程的独立 Signal 峰值，不必每个峰值都占一行。

例如：

-   44.2024 s 电驱功率峰值；
-   44.3225 s Pack 电流峰值；

二者可以在人读表中合并为：

**`44.20～44.32 s｜高负载输出区`**

精确的独立峰值时间继续保存在 CSV 和工程审计中。

### 原则

> **主时间线负责重建实验，不负责替代逐样本数据。**

# 3. `DBC关键Signal覆盖与可读性.md` 改造要求

## 3.1 主体改成一张"本实验核心Signal表"

当前按驾驶输入、条件、请求、反馈、运动、能源、制动拆成多个小表，控制逻辑正确，但人阅读时过碎。

主阅读区合并成一张表。

推荐列顺序：

  ----------------------------------------------------------------------------------------------------
  控制树角色   Signal   Message   CAN ID  单位    本次观测范围/状态   是否变化   解码状态   本次用途
  ------------ -------- --------- ------- ------- ------------------- ---------- ---------- ----------

  ----------------------------------------------------------------------------------------------------

排序必须按照控制关系：

**驾驶输入 → 状态/条件 → 仲裁后请求 → 执行反馈 → 运动反馈 → 能源响应 →
特殊工况**

不要按照 CAN ID 排序。

------------------------------------------------------------------------

## 3.2 Signal名称是主要识别项，CAN ID只是追溯项

禁止在人读附件中只写：

`0x108`

应该写：

`DI_torqueCommand | DI_torque | 0x108 | Nm`

或者：

`BMS_packCurrent | BMS_hvBusStatus | 0x132 | A`

原则：

> **人读报告以 Signal 语义为主，CAN ID 为辅。**

> **CAN ID 主要承担回到原始帧和DBC定义的追溯功能。**

------------------------------------------------------------------------

## 3.4 Pack功率必须作为重要派生量保留

虽然 Pack 功率不是 DBC 原生 Signal，但对车型基线非常重要。

在核心表后明确列出：

**Pack功率（派生）**

`BMS_packVoltage × BMS_packCurrent / 1000`

单位：kW。

要求：

-   同帧计算；
-   正值表示当前报告约定下的放电方向；
-   负值表示净回收方向；
-   明确标记为"派生量"，不要伪装成DBC原生Signal；
-   作为能源响应的重要基线变量保存。

# 4. DBC技术问题单独下沉

以下内容非常重要，但不应该占据核心Signal主表的大量列：

-   DBC DLC；
-   Signal最小所需DLC；
-   ASC实际DLC；
-   解码样本数/帧数；
-   INVALID / SNA；
-   overlapping；
-   不同DBC版本start bit、length、factor、offset差异；
-   同名Signal不同位段；
-   无帧；
-   解码失败原因。

主表中的"解码状态"只使用简洁结果：

-   **正常**
-   **有条件可用**
-   **不可用**
-   **本次无帧**

然后另设：

## DBC异常与可读性说明

只列**确实存在问题或需要特别解释**的Signal。

例如：

  -----------------------------------------------------------------------------------------------------------------------------
  Signal                            状态                    简要说明
  --------------------------------- ----------------------- -------------------------------------------------------------------
  `BMS_packVoltage (0x132)`         有条件可用              DBC声明8字节、ASC实际6字节；该Signal自身只需前2字节，本次完整可读

  `BMS_packCurrent (0x132)`         有条件可用              DBC声明8字节、ASC实际6字节；该Signal自身所需4字节完整，本次可读

  `DI_elecPower (0x266)`            定义需锁定              不同DBC存在同名异位；本次固定采用ONYX定义，不跨版本替换

  `IBST_sInputRodDriver (0x39D)`    来源不同                ONYX无该字段，本次采用Model3CAN 5字节定义

  `DI_brakePedalState (0x118)`      不可用                  本次全程INVALID，不作为制动判据

  `ESP_brakeTorqueTarget (0x145)`   本次无帧                DBC有定义，但本采集域没有该报文
  -----------------------------------------------------------------------------------------------------------------------------

完整技术细节继续保存在工程审计和DBC版本对照CSV中。
