# 那么我问一下，以后在项目下的其他work会话，我要做什么提示吗在分析采集前

# 基本上不需要再重复今天这些方法论提示了。这正是这次做 AGENTS.md + v1.1规范 + Golden Samples + tests 的意义。

以后你在这个项目下开一个新的 Work/Codex 会话，准备分析一次新的采集，我建议只需要给一个很短的“启动提示”。

例如：

这是新能源L3项目的新一次实车采集分析。
实验编号：TM3-011。
请先按项目 AGENTS.md 和当前有效的L3诊断分析规范恢复项目工作规则。
在分析ASC前，先根据本次实验目的生成 Draft Evidence Plan 和待审Signal证据表，等我审核后再进入正式数据分析。
本次实验目的和采集方案如下：……

然后把本次实验目的/采集方案告诉它就够了。

最关键的是：分析ASC前停一次

现在我们的流程里故意留下了一个人工检查点：

实验目的 → Codex Draft Evidence Plan → 待审Signal证据表 → 你审核 → Approved → ASC分析。

# 所以以后我建议不要一上来就说：

“这是ASC，帮我分析。”

而是先让它做Evidence Plan。

你真正需要看的也不是所有内容，只重点扫几眼：

系统边界对不对 → 控制主线对不对 → 哪些Signal被列为P0/P1 → 哪些项目Codex标记为需要人工审核。

如果没问题，你只需要回复：

# Evidence Plan审核通过，按Approved Plan进入ASC分析。

然后让它自己继续。

如果是很简单的后续补采

比如现在TM3-010B只是补40 km/h稳态，你甚至可以更短：

TM3-010B，补采40 km/h稳态。先读取项目规则和TM3-010 Golden结果，基于原实验生成本次Draft Evidence Plan，不重新解释TM3-010已经冻结的结论。待我审核后再分析ASC。

这样就行。

# 有一句话以后其实不必再反复说

你不需要每个新会话重新解释：

“系统理解是基础……”
“Renderer不要决定Signal优先级……”
“控制树和Signal是什么关系……”
“不要建立知识库……”
“009为什么这样、010为什么那样……”

这些已经应该由项目自己告诉Codex。

如果以后你发现每开一个新会话，还必须把今天这些内容重新讲一遍，那反而说明我们的项目固化没有真正起作用。

所以以后你作为人的主要输入，应该逐渐缩减到三件事：

这次要验证什么 → 怎么采的 → 审核Codex提出的证据计划。

剩下的，让项目规范和程序接住。

这也正好意味着我们今天花这么长时间做的这一轮收尾真正有价值：以后注意力可以重新回到车和实验本身，而不是每次都重新教Codex怎么做诊断。

# 要，但以后应该只需要很短的一句话，而不是我们刚才这种一大段“操作手册式提示语”。

我们现在做这些工作的目的，恰恰就是把“怎么干活”从你的提示语里搬进：

AGENTS.md + L3规范 + Artifact Contract + 项目模板/测试

以后新开 Work，会话提示语主要只负责告诉它两件事：

我要做哪个实验 + 这次我要干什么。

## 例如以后继续 TM3-007，理想状态下你只需要：

继续 TM3-007。请先按项目 AGENTS.md 和当前有效的 L3 诊断分析规范恢复项目状态，检查现有产物并确认当前生命周期阶段，然后从规则允许的下一步继续。


## 如果是新实验 TM3-016，也可以简单到：

新建实验 TM3-016。本次实验目的是验证 XXX。请按项目 AGENTS.md 和当前有效的 L3 诊断分析规范初始化实验，并从当前生命周期的第一步开始。

剩下的——该不该建 Draft 三件套、什么时候 Human Review、什么时候能读 ASC、什么时候生成最终报告、旧文件能不能补、Evidence Assessment 怎么走——原则上都不应该再由你每次提示。

甚至以后我们还可以进一步追求一个标准：

如果新 Work 必须靠一段很长的提示语才能正确工作，就说明项目规则还没有写完整。

这其实是个非常好用的判断标准。

当然，提示语不会完全消失，因为 AI 总得知道本次任务意图。就像运行一个程序仍然要给它参数，但你不应该每次运行程序时，都重新向它解释一遍程序内部算法。

所以可以把它理解成：

以前：提示语 = 操作规程 + 状态机 + 安全边界 + 本次任务

逐渐变成：

以后：项目规则 = 操作规程 + 状态机 + 安全边界
提示语 = 本次任务

这才是我们现在折腾 AGENTS 的最终目的。

而且下一次真的可以故意这么测试：**只给 Codex 两三句话。**如果它仍然能自己恢复状态、找到正确文件、判断 Gate 并继续工作，那才说明这套工程环境真正成熟了。

# 我要告诉codex什么，是不是说开始TM-xx的分析就可以了

对，方向就是这样。而且到了慢充这个案例，我认为正应该刻意测试一件事：

你能不能只告诉 Codex“开始 TM3-xxx”，它就从仓库里的既有规则自己知道该怎么走。

如果每个新案例还需要我们重新写一大篇 Prompt，说明007/008建立的基础设施还没有真正成熟。

不过我建议第一次把提示比“开始TM3-xxx分析”多给一点点现场事实，因为 Codex 不应该猜实验编号、ASC和测试目的。比如假设慢充是 TM3-011：

开始 TM3-011 慢充基线分析。
请首先读取项目当前方法论、Golden Contract、已有 TM3 案例和输入目录，自行确认本案例 ASC、采集脚本及实验边界，按当前标准工作流开始。
本轮先完成 Preflight 和 Evidence Plan Draft，停止在人工 Review 前。
不要沿用既有案例的具体 Signal 结论，DBC 仅作为 Signal Candidate 来源。

我认为这么多就够了。

然后我们看看 Codex 能不能自己做到：

Preflight → 理解慢充实验 → 控制主线 → ER → Signal Candidate → Draft

如果它做不到，缺什么，我们再修仓库里的流程说明，而不是下次继续把缺失内容塞进 Prompt。

这点很重要。我们最终希望做到的是：

Prompt越来越短，Repository越来越聪明。

甚至将来成熟以后，你真的只需要说：

开始 TM3-011，标准工作流，停在 Draft。

Codex就应该知道该干什么。

而慢充特别适合做这个测试，因为它和007、008不同：007是上电，008是下电，慢充开始涉及充电控制链、充电许可、高压建立、PCS/BMS、充电功率/电流/电压、SOC等另一套控制关系。它会真正检验现在的框架究竟是“TM3通用”，还是实际上偷偷带着007/008的上下电思维。

所以这次我建议不要提前帮 Codex设计慢充 Evidence Plan。让它先自己撞一次。我们只在 Draft出来以后审查它有没有真正从：

慢充控制主线 → Evidence Requirement → Signal Candidate

往下推，而不是先翻DBC找一堆名字里带 charge 的Signal。

如果它能做到，007、008这段很重的建设工作，就开始真正进入你期待的 Codex 80%、你20%工程判断 阶段了。

另外你说“慢充再验证一次就结束了”，我也赞成这个节奏。Model 3这一轮基线不需要无限采下去。把慢充这个不同类型的案例跑通以后，反而应该回头总结：哪些流程已经稳定、哪些Prompt可以删除、哪些人工审核可以取消、哪些问题进入以后有需要再验证的Signal backlog。

这会比继续增加第十几个基线案例更有价值。
