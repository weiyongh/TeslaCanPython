# 那么我问一下，以后在项目下的其他work会话，我要做什么提示吗在分析采集前

# 基本上不需要再重复今天这些方法论提示了。这正是这次做 AGENTS.md + v1.1规范 + Golden Samples + tests 的意义。

以后你在这个项目下开一个新的 Work/Codex 会话，准备分析一次新的采集，我建议只需要给一个很短的“启动提示”。

例如：

这是新能源L3项目的新一次实车采集分析。
实验编号：TM3-011。
请先按项目 AGENTS.md 和当前有效的L3诊断分析规范恢复项目工作规则。
在分析ASC前，先根据本次实验目的生成 Draft Evidence Plan 和待审Signal证据表，等我审核后再进入正式数据分析。
本次实验目的和采集方案如下：……

然后把本次实验目的/采集方案告诉它就够了。

最关键的是：分析ASC前停一次

现在我们的流程里故意留下了一个人工检查点：

实验目的 → Codex Draft Evidence Plan → 待审Signal证据表 → 你审核 → Approved → ASC分析。

# 所以以后我建议不要一上来就说：

“这是ASC，帮我分析。”

而是先让它做Evidence Plan。

你真正需要看的也不是所有内容，只重点扫几眼：

系统边界对不对 → 控制主线对不对 → 哪些Signal被列为P0/P1 → 哪些项目Codex标记为需要人工审核。

如果没问题，你只需要回复：

# Evidence Plan审核通过，按Approved Plan进入ASC分析。

然后让它自己继续。

如果是很简单的后续补采

比如现在TM3-010B只是补40 km/h稳态，你甚至可以更短：

TM3-010B，补采40 km/h稳态。先读取项目规则和TM3-010 Golden结果，基于原实验生成本次Draft Evidence Plan，不重新解释TM3-010已经冻结的结论。待我审核后再分析ASC。

这样就行。

# 有一句话以后其实不必再反复说

你不需要每个新会话重新解释：

“系统理解是基础……”
“Renderer不要决定Signal优先级……”
“控制树和Signal是什么关系……”
“不要建立知识库……”
“009为什么这样、010为什么那样……”

这些已经应该由项目自己告诉Codex。

如果以后你发现每开一个新会话，还必须把今天这些内容重新讲一遍，那反而说明我们的项目固化没有真正起作用。

所以以后你作为人的主要输入，应该逐渐缩减到三件事：

这次要验证什么 → 怎么采的 → 审核Codex提出的证据计划。

剩下的，让项目规范和程序接住。

这也正好意味着我们今天花这么长时间做的这一轮收尾真正有价值：以后注意力可以重新回到车和实验本身，而不是每次都重新教Codex怎么做诊断。
