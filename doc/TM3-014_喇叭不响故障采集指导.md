# TM3-014 喇叭不响故障采集指导

版本：2026-08-31。状态：故障现象已由用户报告；故障部件、声音来源和信号实车适配均待验证。

## 1. 诊断问题

用户现象：方向盘中央左右位置按压不响，但锁车有怪叫声。

本次区分三种请求来源：方向盘喇叭垫、Tesla官方App鸣笛、原设置下的锁车动作。要回答：物理按压是否被识别？不同请求是否产生VCFRONT喇叭开启状态？有状态时是否实际发声？锁车声音是否与该状态同步？

锁车有声不证明常规喇叭正常。Tesla手册说明Boombox可使用PWS车外扬声器播放声音，但本车怪叫声是否来自它仍未知，须保留声音设置和录音。首轮不改变任何音效设置，也不把“怪叫”直接判定为自定义音效或机械故障。

## 2. 安全和前置条件

- 全程安全驻车、P挡，不挂D/R、不做道路试验。喇叭功能未恢复前暂停此前的加速和匀速道路采集，安排维修确认。
- 选择允许短时鸣笛且不扰民的位置，告知附近人员，录音人员不贴近声源。
- 只正常按压中央喇叭垫；不敲击、不拆气囊、不拔方向盘或SRS插头、不短接线路、不向总线注入报文。
- 首轮保存故障原状，不重启、不清码、不更新软件、不改变声音设置；已有告警只拍照，不在采集中执行诊断清除。
- 保持方向盘回正、驾驶门关闭、车辆已唤醒，音乐和其他背景声关闭。不会发声也不加大按压力度或长按。
- 锁车段所有人和宠物离车，钥匙随身。选用故障发生时的原锁车方式，并记录自动锁车的实际时刻。

## 3. 设备与证据

X930：使用已经验证的车辆CAN接入点，全程只监听，全量保存原始ASC；不只过滤喇叭ID，不变更已有正确接线和终端配置。

录音/视频：建议另一台设备在安全位置连续记录。拍到按压位置和手部释放，车外录音记录实际声音。开始时口述“TM3-014，脚本零秒”，记录ASC开始与脚本开始的偏移。CANVoiceRunner的触发CSV是提示时间，不是手实际按下时间。

Tesla官方App：只用于两次远程“鸣笛”对照。记录点击、成功/失败提示及实际响应，网络延迟不能当作CAN控制延迟。App不可用则跳过，不影响方向盘和锁车两段保留。

OBDLink MX+ / Scan My Tesla：本次不是必需。尚未确认App提供喇叭开关与输出信号，因此不要依赖它判定输入故障。若已接好且能稳定记录低压电压，可作为背景辅助；不得为此中途换线、丢失X930记录。它与Tesla官方App不是同一个工具。

## 4. DBC观察清单

主用DBC：`input/tesla_model3_ONYX.dbc`，均为第三方定义，需实车验证。bit和byte从0开始，均为Intel小端1-bit字段。

| ID | 信号 | 有效条件 / 位置 | 观察角色 |
|---|---|---|---|
| 0x3C2 | VCLEFT_hornSwitchPressed | switchStatusIndex=0；起始bit2，即byte0 bit2 | 按压输入状态 |
| 0x2E1 | VCFRONT_hornOn | statusIndex=0；起始bit51，即byte6 bit3 | 喇叭开启逻辑状态，非电流反馈 |
| 0x273 | UI_honkHorn | 起始bit61，即byte7 bit5 | UI请求候选；是否对应App须本次验证 |
| 0x3B3 | UI_soundHornOnLock | 起始bit4，即byte0 bit4 | 锁车鸣笛设置，不是发声反馈 |
| 0x2A9 | EPBL_hornRequest | 起始bit48，即byte6 bit0 | 其他请求背景，不主动触发EPB |
| 0x2E8 | EPBR_hornRequest | 起始bit48，即byte6 bit0 | 其他请求背景，不主动触发EPB |

0x3C2的复用索引是byte0低2位；0x2E1的复用索引是byte0低3位。只在对应索引为0的帧解读目标bit。没有该页或帧丢失时标记“不可观测”，不填0，不将上一页数值强行延续为实时值。

同时观察车辆挡位、唤醒状态、低压供电背景和相关帧周期。不要把未出现的故障报文解释为“无故障”。

## 5. 执行和窗口

使用同目录关联的TXT脚本，第一行仅播报短动作，详细说明提前阅读。1秒按压后自行松开，不等待下一节点。左、中、右各重复两次，App两次、锁车两次。

- 方向盘：以真实按下/松开时间分别建事件，保留动作前3秒至释放后5秒；每次按压之间保留无操作背景。
- App：从点击前5秒保留到实际响应结束后5秒，同时保留点击至响应的完整等待段。失败单独标记。
- 锁车：以实际锁止及声音时刻为准，保留前5秒至后10秒。离座、关门和锁车分别标记。
- 没有声音本身就是有效结果；只要视频/现场记录能确认动作完成，就不因无声删除该段。
- 若意外自动落锁、重试或有其他操作，记录真实时序；不为了符合计划时间虚构事件。

## 6. 判读与异常分支

目标链：请求来源 → 状态条件 → 控制器开启逻辑 → 输出电路（本次未直接测量）→ 声音结果。

| 实测组合 | 可支持的排查方向，不等于部件确诊 |
|---|---|
| 按压信号变化，hornOn变化，但无声 | 输入已被识别；后续检查输出级、供电、线束、喇叭本体，也需核实hornOn语义 |
| 按压信号变化，hornOn不变 | 查控制条件、请求传递及定义适配；不能直接判定VCFRONT损坏 |
| 按压信号不变，App能产生hornOn且正常鸣笛 | 输入开关/输入路径优先，但须确认0x3C2页面有效；不能凭此区分开关、线束或控制器 |
| 仅某个按压位置偶尔有效 | 记录位置、力度和重复性，输入接触路径为候选，不自行拆气囊 |
| App和按压均不响 | 两种请求链分别检查；App失败/超时不是执行链失败证据 |
| 锁车有怪叫，但hornOn未变化 | 声音可能走其他路径，或CAN定义/页面不适配；录音与设置用于进一步区分 |

任何情况下hornOn=1都不证明喇叭端已有供电或实际电流；CAN只能把排查收敛到一段链路。测量输出电路、气囊附近线路或更换部件应交由合格维修人员，依据对应车辆维修资料进行。

同一编号保存上述所有文件。首轮是故障样本，不写为正常值；如后续维修恢复，保持相同接线和条件重做，文件增加`_修复后_R1`用于对照。

分析时使用SavvyCAN加载ASC与DBC，先核对六个ID及两类复用页面，再对齐视频动作和声音；保留原始字节以复核DBC解码。现有自动动作筛选程序是否识别喇叭关键词尚未验证，不直接依赖其自动排名。实际分析命令和输出文件在分析报告中记录。
