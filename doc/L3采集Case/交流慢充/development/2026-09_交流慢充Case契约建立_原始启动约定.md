## 1. 本轮任务目标

本轮不是一次性生成全部慢充采集脚本，也不是建立完整的“脚本生成平台”。

先以一个真实 Case 作为样板，建立并验证一条最小、可用的生成链路：

```text
L3 Evidence Requirement
        ↓
Observable Requirement
        ↓
Candidate Signal / 外部证据
        ↓
Experiment Event
        ↓
VoiceRunner Script
```

第一阶段样板：

```text
Case    = L3-Charge-Slow-FullCycle
Vehicle = TESLA-M3-SOP5
```

核心目标：

> 利用一个真实的 `L3-Charge-Slow-FullCycle` Case，建立从 L3 Evidence Requirement 到现场 Event，再到 CANVoiceRunner 可执行脚本的最小生成方法；首先证明这条链路可用，而不是一次性建立完整的慢充脚本体系。

---

## 2. 输入

本任务可以使用以下已有信息：

- L3慢充知识与已确认的控制主线、控制树、状态和变量；
- 已定义的 Case；
- `TESLA-M3-SOP5` 车型信息；
- 已有 DBC 与 Candidate Signals；
- CANVoiceRunner 当前真实具备的脚本、播报、暂停、照片、备注、录音和导出能力。

DBC 的定位必须保持为：

> 用于评估 Case 的可观测性和寻找 Candidate Signal，不得由 DBC Signal 反向定义 Case；当前 Signal 语义均视为候选，未经实车验证不得提升为 Evidence。

---

## 3. 第一阶段输出

第一阶段只要求形成：

1. `Experiment Plan`；
2. CANVoiceRunner 可执行脚本；
3. `Evidence Requirement ↔ Event ↔ Candidate Signal / 外部证据` 的对应关系；
4. 现场需要人工补充的照片、备注等要求。

当前阶段不输出：

- 诊断结论；
- Evidence 判定结果；
- Signal 语义确认结果；
- 车型基线结论；
- 其余四个慢充 Case 的正式脚本。

只有 `L3-Charge-Slow-FullCycle` 样板经过人工审核和真实采集验证后，再讨论其他 Case 是否沿用、调整或简化该方法。

## 4. 关键语义边界

### 4.1 Evidence Requirement 不是 Evidence

采集前只能定义“需要证明什么”和“需要观察什么”。

正式 Evidence 必须来自真实采集和后续分析，不能在脚本设计阶段预设为已经成立。

### 4.2 Event 的语义

VoiceRunner Event 只描述：

- 人工需要执行的动作；
- 现场需要观察或确认的事实；
- 需要拍照、备注、录音的节点。

不得把预计的车辆内部状态或 CAN Signal 变化写成已经发生的事实。

例如：

```text
正确：
现在插入充电枪
观察车辆是否显示已连接
确认充电已经开始后拍照
现在通过正常入口停止充电

错误：
BMS_acChargeEnable变为1
OBC进入Ready
高压路径已经建立
Pack开始充电
```

后者属于待观察、待分析、待验证对象。

### 4.3 VoiceRunner 不是自动实验控制器

当前 CANVoiceRunner 的真实工作方式仍然是“播报驱动的人机协作采集”，因此第一版不要设计超出现有能力的自动条件状态机。

基本模式应保持：

```text
播报动作
↓
操作者执行
↓
留出观察窗口
↓
必要时人工确认 / 拍照 / 备注
↓
继续下一 Event
```

所谓“条件”，当前主要是人的现场确认条件，而不是程序实时读取 CAN 后自动决定状态迁移。

## 5. FullCycle 的讨论起点

当前先讨论：

```text
Case：L3-Charge-Slow-FullCycle
Vehicle：TESLA-M3-SOP5
用途：正常慢充完整生命周期基线
```

核心命题：

> Model 3 从交流充电未连接状态开始，经过连接识别、车辆准备、交流供电、OBC 功率转换和 Pack 充电，再经正常人工停止、解锁和拔枪退出时，各层状态、控制关系、能量变化和关键时序是什么？

本 Case 不承担：

- 预约充电状态门；
- 电流上下调阶跃；
- 长时间热稳定；
- 自动达到 SOC 上限；
- 故障注入或异常拔枪。

这些问题保留给其他独立 Case。

## 6. 下一步讨论顺序

现在不要先写 VoiceRunner 脚本，也不要先从 DBC Signal 倒推实验。

首先只完成：

> **`L3-Charge-Slow-FullCycle` 到底需要证明什么？**

请先提出该 Case 的 `Evidence Requirements` 草案，建议控制在 **5～8 条**。

审核并冻结 Evidence Requirements 后，再依次进入：

```text
Evidence Requirement
↓
Observable Requirement
↓
Candidate Signal / UI / EVSE / Photo / Note
↓
Event
↓
Experiment Plan
↓
VoiceRunner Script
```

不要因为流程设计本身继续增加新的正式阶段、对象或架构；只有真实采集需求证明有必要时再增加。

---

## 7. 当前工程原则

本任务遵循：

> **够用、实用是一切工作的出发点。**

FullCycle 的使命首先是把一条真实链路跑通，并通过实车采集检验它是否好用。

如果一个设计不能明显提高现场采集质量、Evidence 可追溯性或后续分析可靠性，就暂时不要加入。
