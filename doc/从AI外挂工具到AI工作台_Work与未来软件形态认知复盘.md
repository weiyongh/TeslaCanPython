# 从"AI外挂工具"到"AI工作台"：我对 Work 与未来软件形态的一次重新理解

> 记录时间：2026-09-10\
> 性质：个人工作方法与软件形态认知复盘

## 1. 这次真正恍然大悟的是什么

过去我对 GPT 工具能力的理解，仍然建立在传统软件的心智模型上：ChatGPT
是会聊天、会推理的 AI，Notion、Google
Docs、文件、代码工具等则像外挂或插件。

这种理解不能说错，但太窄了。

``` text
ChatGPT
├─ 对话
├─ 推理
└─ 外挂工具
   ├─ Notion
   ├─ Google Docs
   ├─ Files
   ├─ Python
   └─ 其他插件
```

今天通过 TeslaCanPython、CANVoiceRunner、L3 Case、Acquisition Plan
这一整套实际工作的讨论，我突然看到了另一种软件形态：

> **不是给 AI 挂上越来越多的软件工具，而是把 AI
> 放到工作的中心，让它理解人的工作意图，再组织和调用各种软件能力完成工作。**

``` text
                  人
                  │
           用自然语言表达目标
                  │
                  AI
          ┌───────┴───────┐
          │               │
      理解专业语义     组织工作过程
          │               │
          └───────┬───────┘
                  │
            调用具体能力
      ┌───────────┼───────────┐
      │           │           │
   本地代码     Notion      Docs / Files
      │           │           │
      └───────────┼───────────┘
                  │
              完成工作
```

这不是"聊天机器人 + 插件"的简单升级，而是**软件使用方式的变化**。

## 2. Work 不是更大的聊天框，而是一张工作桌

我过去容易把 Work
理解成一个更强、更持久、能操作文件和代码的聊天区域。今天才真正理解，它更像一张已经布置好的**工作桌**。

桌子上可以放项目资料、专业知识、代码、文档、数据、工具、外部软件能力，以及已经形成的工作规则和方法。

人走到这张桌子前，不再首先考虑：

> 我要打开哪个程序？我要运行哪个
> Python？我要点哪个菜单？我要把哪个文件复制到哪里？

而是直接说：

> **"今天我要完成什么工作。"**

AI 理解目标以后，再去使用这张桌子上的工具。

这就是今天非常形象的比喻：

> **我走到一张摆着锅铲的 Work 桌子前，说今天炒什么菜，然后开火炒菜。**

我不需要先研究锅铲制造工艺，也不需要亲自成为厨房里每一台设备的操作员。

## 3. 从"人操作软件"到"人驾驭 AI，AI 操作软件"

传统软件时代：

``` text
人的目标
   ↓
判断使用哪个软件
   ↓
打开软件
   ↓
寻找菜单 / 按钮 / 命令
   ↓
输入参数
   ↓
导出结果
   ↓
切换另一个软件
   ↓
继续加工
   ↓
完成工作
```

软件提供能力，但**工作流程主要存在于人的脑子里**，人实际上是所有软件之间的集成器。

AI Work 带来的变化可能是：

``` text
人的目标
   ↓
自然语言告诉 AI
   ↓
AI理解工作语义
   ↓
AI组织任务
   ↓
AI调用不同软件 / 工具 / 文件 / 代码
   ↓
需要专业判断时交还给人
   ↓
继续执行
   ↓
完成工作
```

因此人的角色逐渐不再只是"软件操作员"，而是：

> **目标提出者 + 专业判断者 + 审核者 + AI工作过程的驾驭者。**

这对我尤其有意义。我的目标本来就不是成为专业软件工程师，而是做新能源诊断：

> **懂软件，因此能够驾驭 Codex；懂诊断，因此知道 Codex 应该做什么。**

## 4. TeslaCanPython 让我第一次把这种软件形态看清楚

这次认知不是抽象讨论得来的，而是从一个具体问题里长出来的。

``` text
L3 Knowledge
      ↓
Case
      ↓
Evidence Requirement
      ↓
Observable Requirement
      ↓
人工审核 / 冻结 Case Contract
      ↓
现场条件
      ↓
AI设计采集
      ↓
Acquisition Plan
      ↓
确定性共享实现
      ↓
VoiceRunner Script
      ↓
实车 Round
      ↓
ASC / Photo / Note / Observation
      ↓
Evidence
      ↓
车型实例化与诊断理解
```

以前很容易把共享实现理解成"一个生成 VoiceRunner TXT 的 Python 程序"。

现在才看清楚：

> **共享实现只是 Work 桌上的一件专业工具。**

正常工作时，我面对的是 Codex：

> "我想做一个空调制冷建立 Case，开始吧。"

``` text
我 + AI
讨论 L3 和 Case 边界
        ↓
形成 ER / OR
        ↓
我审核
        ↓
Contract 冻结
        ↓
我告诉 AI 现场条件
        ↓
AI形成 Acquisition Plan
        ↓
AI在后台调用共享实现
        ↓
生成 VoiceRunner Script
        ↓
我审核
        ↓
上车采集
```

JSON、Schema、Python CLI、Renderer
调哪个函数，这些都应该逐渐退到"后厨"。

## 5. AI 与确定性代码不是竞争关系

AI 化并不意味着所有东西都应该交给 AI。合理的软件形态应该让 AI
和传统确定性代码各做自己擅长的事情。

### AI负责

``` text
Case Contract + 现场条件
        ↓
Acquisition Plan
```

包括理解 L3 语义、理解自然语言现场条件、设计 Event、安排观察窗口、建立
OR ↔ Event 关系、编写现场语言、根据约束调整实验方案。

### 确定性代码负责

``` text
Acquisition Plan
        ↓
结构校验
        ↓
Renderer
        ↓
VoiceRunner Script
```

包括 Schema、字段和引用校验、时间顺序、OR 覆盖、输出格式、VoiceRunner
解析兼容性，以及其他可重复、稳定的机械性工作。

因此未来软件不是"AI 把传统软件全部吃掉"，而更可能是：

> **AI成为语义和工作组织层，传统代码成为可靠、确定、可复用的能力层。**

## 6. 工具不是中心，人的专业目标才是中心

今天最重要的视角变化，是不再从"软件有什么功能"出发，而是从：

> **我要解决什么专业问题？**

出发。

新能源诊断真正的主线是：

``` text
诊断目标
   ↓
系统理解
   ↓
Case
   ↓
实验
   ↓
采集
   ↓
Evidence
   ↓
分析
   ↓
诊断判断
```

TeslaCanPython、VoiceRunner、Python、Notion、Google Docs、CAN
卡、ASC、DBC 都只是不同位置上的工具。

可以把整个工作压缩为：

> **我的诊断目标 → AI理解 → 工具执行 → 实车 Evidence → 回到诊断判断。**

软件不再主导我的工作方式，软件开始服务于我的工作方式。

## 7. 不同的 Work，就是摆着不同工具的桌子

``` text
采集设计 Work
→ L3
→ Case
→ Contract
→ Acquisition Plan
→ VoiceRunner Script
```

``` text
ASC分析 Work
→ Round
→ Observation
→ Retrieval
→ Signal分析
→ Evidence
→ Assessment
```

``` text
故障诊断 Work
→ 故障现象
→ 控制树
→ Evidence
→ 诊断树
→ 结论
```

``` text
知识沉淀 Work
→ 已审核结论
→ L3知识结构
→ Case经验
→ Notion / 文档
```

人还是同一个人，AI 还是 AI。区别只是：

> **走到不同桌子前，AI拿起不同的锅铲。**

这比"给 ChatGPT 装几个插件"的理解大得多。

## 8. 软件 UI 可能从"功能入口"转向"工作意图入口"

传统软件 UI 的核心问题通常是：

> 你要使用哪个功能？

所以有菜单、工具栏、对话框、表单、参数页、命令和工作流按钮。

AI 工作环境的核心问题则逐渐可能变成：

> **你想完成什么工作？**

于是入口从：

``` text
功能 → 操作 → 结果
```

逐渐变成：

``` text
意图 → 对话与确认 → AI组织工具 → 结果
```

这不意味着 GUI 会消失。CANVoiceRunner
在车旁边仍然需要清晰按钮、状态显示、语音播报、拍照、备注、开始/暂停/结束，以及稳定确定的执行行为。

变化的是：

> **人不再需要亲自操作整个软件链条。**

## 9. Contract、Reference、Acquisition Plan 也因此找到了位置

### Case Contract

是"题目要求"：这个 Case 是什么，必须证明什么，最低需要观察什么关系。

### 现场条件

是"考场条件"：今天这台车、这个环境、这些设备和限制下，可以怎么做。

### Reference

是"经过人工审核的参考答案"。它不是模板，也不是强制流程，而是告诉
AI：以前一个相似问题曾怎样被合理实例化。

### Acquisition Plan

是 AI 根据题目和现场条件形成的：

> **这一次准备怎么采。**

### 共享实现

是桌上的专业工具：把 AI
形成的采集计划稳定地校验、转换成具体执行工具需要的产物。

### VoiceRunner

是当前现场执行终端。

### Round

是真正上车做了一次实验。

### Evidence

是实验之后，通过真实数据和分析最终能够证明的东西。

这些概念终于不再是散落的术语，而是各有明确位置。

## 10. 软件工程本身也会发生变化

传统开发通常从"用户需要什么功能"开始：

``` text
用户需要什么功能？
↓
设计页面
↓
设计菜单
↓
设计按钮
↓
设计数据库
↓
实现功能
↓
让用户学习怎么使用
```

AI 原生的软件可能越来越像：

``` text
用户真正要完成什么工作？
↓
哪些语义必须由人和AI讨论？
↓
哪些专业判断必须由人审核？
↓
哪些工作可以由AI组织？
↓
哪些部分需要确定性代码保证？
↓
AI可以调用哪些现有工具？
↓
最后才决定还需要什么传统UI
```

软件设计的中心可能从**功能**逐渐转向**工作**，从"人怎样使用软件"逐渐转向"人怎样与
AI 一起完成工作"。

## 11. 对我个人最重要的变化

以前面对 Codex，多少还有一种传统开发思维：

> 我要想清楚程序怎么设计，然后让 Codex 帮我写。

现在逐渐变成：

> **我要把诊断问题和工作目标想清楚，让 Codex
> 和我一起形成方案，再让它调用软件能力实现。**

我的核心能力不应该变成 Python 写得多熟、JSON 记得多清楚、CLI
会多少、能不能亲自实现所有模块。

而应该继续加强：

-   系统理解；
-   控制树；
-   Evidence 思维；
-   Case 设计；
-   实车体感；
-   数据分析；
-   故障边界判断；
-   对 AI 输出的工程审核能力。

因此长期定位可以压缩成一句话：

> **我不是要成为一个被 AI 带去写软件的人，而是要成为一个懂软件、能驾驭
> AI 和软件工具的新能源诊断者。**

## 12. 这次认知也带来一个重要警戒

一旦看见这种新的软件形态，很容易马上想到 Agent
平台、自动编排、插件系统、通用工具框架、多
Renderer、知识图谱、自动工作流、全系统集成。

但这恰恰可能重新掉回旧陷阱。

> **够用、实用，是一切工作的出发点。**

当前真正需要验证的闭环仍然很简单：

``` text
聊一个新 Case
        ↓
形成 Contract
        ↓
给出现场条件
        ↓
AI形成 Acquisition Plan
        ↓
调用共享实现
        ↓
生成 VoiceRunner Script
        ↓
人工审核
        ↓
实车 Round
        ↓
形成 Evidence
```

这个闭环真正跑通一次，比提前设计十个未来平台更有价值。

## 13. 今天真正"找到北"的地方

前些天一直在
Case、ER、OR、Reference、VoiceRunner、Round、共享实现、Codex、Work
之间来回讨论。每一个东西单独都能理解，但一直隐约有一个问题：

> **我到底在造什么？**

今天终于可以回答：

> **我不是在造一个越来越复杂的软件系统。**

我是在逐渐建立：

> **一个以我的新能源诊断方法为核心，以 AI
> 为工作组织层，以各种软件和代码为工具层，以实车 Evidence
> 为落点的个人专业工作环境。**

``` text
我
→ 决定方向与专业判断

AI
→ 理解语义、组织工作、调用工具

确定性代码
→ 提供可靠、可重复的专业能力

现场软件
→ 提供稳定的人机执行界面

实车
→ 提供真实世界事实

Evidence
→ 决定结论能不能成立
```

这可能就是我今天真正理解的 Work。

## 14. 最后一句话

过去几十年的软件训练我们：

> **学习怎样操作软件。**

AI 时代可能越来越要求我们学习：

> **怎样把自己的专业工作说清楚、组织清楚、判断清楚，然后让 AI
> 驾驭软件替我们完成那些本来需要自己操作的部分。**

对我来说，这个变化最终可以浓缩成一句：

> **软件逐渐退到后台，专业工作重新回到前台。**

而 Work，就是那张已经摆好锅铲、等我坐下来开工的桌子。
