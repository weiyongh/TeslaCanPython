# Acquisition Plan采集计划设计方案

**设计版本：** v0.3  
**形成日期：** 2026-09-10  
**设计状态：** 已审核通过  
**实现状态：** 第一版已实现并完成Human Review  

## 1. 设计目标

建立服务于TeslaCanPython当前单车、单人、人工审核工作流的Acquisition Plan（采集计划）工具，使不同L3 Case经过相同路径形成采集计划，并由当前唯一的VoiceRunner Renderer生成符合现场工作单风格的语音执行脚本。

本设计使用以下已审核输入验证：

- `L3-Charge-Slow-FullCycle` Case契约及脚本Reference；
- `L3-Charge-Slow-CurrentControl` Case契约及脚本Reference。

两者分别代表生命周期/状态迁移型Case与控制输入/实际响应型Case。第一版不再增加验证Case。

## 2. 总体关系

```text
L3 Knowledge
→ Case
→ ER
→ OR
→ 人工审核并冻结Case契约

已审核Case契约
+ 用户提供的自然语言现场条件
+ 公共生成规则
→ AI草拟Event与OR映射
→ Acquisition Plan
→ 代码结构校验
→ VoiceRunner文本渲染
→ 人工审核
→ 可执行Script
```

Case契约是规范性语义输入；Acquisition Plan是连接L3 Case语义和具体执行输出的公共中间体；脚本Reference是示例性预期输出。发生冲突时以Case契约为准，Reference不得反向增加或修改ER、OR。

## 3. 输入

### 3.1 已审核Case契约

Case契约采用统一Markdown结构：

```text
基本信息
1. Case目标
2. Case范围
3. Evidence Requirements
4. Observable Requirements
5. Case边界
```

代码只读取`Case ID`、ER ID、OR ID及其所属ER。代码不解释ER、OR自然语言语义，不从Case名称推导动作，也不根据具体Case ID选择专用逻辑。

### 3.2 自然语言现场条件

用户继续用自然语言说明实际现场情况，例如可执行动作与入口、设施启动停止方式、可见页面与读数、不可控等待、不确定项和安全限制。用户不需要填写Schema或表单。

AI负责将这些文字转化为Event草案所需约束；代码不尝试理解自然语言。现场条件不进入Case契约，也不反向定义Case、ER或OR。

### 3.3 公共生成规则

公共规则至少包括：

- Case契约不包含Vehicle ID或具体车型；
- 一个Event只保留一个清晰主动作或一个必要观察节点；
- Event第一行标题是唯一播报内容，必须使用简短、清晰且可直接执行的现场语言；其余说明行不参与播报；
- VoiceRunner在每个Event前自动倒数，并以提示音作为操作者执行动作的时间锚点；Script不重复写入倒计时内容；
- 不要求操作者判断不可见的内部状态；
- 计划时间只用于现场节奏，不作为实际事件事实；
- Event之间的计划等待必须具有明确实验或采集意义，例如动作前基线、响应观察或稳定观察窗口，不作为设备准备或信息登记时间；
- 时间预算必须包含真实现场动作、人员移动、设备切换、页面操作、拍照取证和下一Event倒计时前的就位余量；
- 同一功能有多个现场入口时，应在生成Script前选择不干扰持续采集、时间锚点明确、操作路径稳定且认知负担较低的方案，不把未决选项留给操作者在Event到点时临时决定；
- 设备、软件和车型实现名称只有在本次现场条件明确提供且确实改变操作步骤、安全边界或Evidence解释时才进入Script；否则使用准确的功能动作表达；
- 当ER需要跨来源联合观察时，应在同一短时窗口连续取得相关来源，并在有持续性要求时于后续稳定窗口重复同类联合观察；来源刷新时间未知时只声明共同状态，不作精确同步或定量等同；
- 现场只强制取得对当前Case有实际Evidence价值且自然可得的信息；页面自然附带的信息可以保留，但不得为追求字段齐全增加操作、抄录或等待负担；
- 停止、解锁、释放等相邻步骤如果是不同的人工动作或需要独立时间锚点，应保持为不同Event，不因控制主线相邻而合并；
- 不可控等待允许暂停或顺延，安全条件优先；
- Candidate Signal和DBC不参与Script生成；
- Round由CANVoiceRunner一次Start到Stop形成，生成器不创建Session领域对象。

### 3.4 脚本Reference

Reference用于核对现场表达风格、检查观察窗口、提供Renderer回归样例并防止Case专属实现。Reference不是模板文本，不要求新脚本逐字复制，也不是共享代码的生成规则。

## 4. AI职责

AI负责：

1. 读取已审核Case契约及用户现场条件；
2. 保持Case、ER、OR不变；
3. 为OR安排必要动作、前后对照和观察窗口；
4. 选择合理的Event顺序和计划时间预算；
5. 将现场条件转化为直接、简短的操作者语言；
6. 加入必要的安全、暂停、顺延和无效条件；
7. 为每个Event标注其承载的OR；
8. 输出Acquisition Plan草案。

采集前准备应在用户点击Start、Round正式开始之前完成。00s从Round正式开始起算；若CAN记录必须在Round开始后由操作者立即启动，应将该动作明确放在00s，并为第一个车辆动作保留有实验意义的CAN基线窗口。现场工作可执行性与L3实验验证充分性共同决定Event顺序和计划时间，不能只按控制逻辑机械排点。

AI不得：

- 从DBC或Candidate Signal生成Case、ER、OR或Event；
- 因现场不可见而删除或降低ER、OR；
- 把推测的内部状态写成操作者已确认的事实；
- 为补齐信息自行假设启动方式、显示能力或安全入口；
- 修改已审核Case契约。

现场条件不足以形成安全、可执行Event时，AI应指出具体缺口并停止生成，不由代码或默认值补造。

## 5. 代码职责

代码只负责确定性工作：

1. 读取统一结构的Case契约，取得Case ID、ER ID和OR ID；
2. 承载AI给出的Acquisition Plan；
3. 校验字段、OR引用、事件顺序和时间合法性；
4. 将中间模型渲染为CANVoiceRunner可解析TXT；
5. 对渲染结果执行解析兼容性检查；
6. 返回明确错误，不自动修正语义。

代码不得调用LLM、自动生成ER/OR/Event语义、按Case ID写专用分支、读取DBC/ASC/Candidate Signal，也不得建设工作流引擎、数据库、资产索引或版本管理系统。

## 6. Acquisition Plan最小模型

Acquisition Plan只保存生成和校验当前执行输出所需字段。建议采用JSON，便于AI生成、代码读取和测试固定；模型本身不使用VoiceRunner专属命名。

```json
{
  "schema_version": "acquisition-plan-v1",
  "case_id": "L3-Charge-Slow-FullCycle",
  "contract_ref": "doc/L3采集Case/交流慢充/L3-Charge-Slow-FullCycle_Case契约.md",
  "events": [
    {
      "planned_time_s": 0,
      "title": "开始采集",
      "instruction_lines": ["交流慢充连接、启动、稳定充电及正常退出"],
      "or_refs": ["OR-01.1"]
    }
  ]
}
```

### 6.1 顶层字段

| 字段 | 必需 | 作用 |
| --- | --- | --- |
| `schema_version` | 是 | 第一版仅接受`acquisition-plan-v1` |
| `case_id` | 是 | 必须与Case契约中的Case ID完全一致 |
| `contract_ref` | 是 | 工作区相对路径字符串，指向本次使用的已审核Case契约 |
| `events` | 是 | 按计划顺序保存Event草案 |

### 6.2 Event字段

| 字段 | 必需 | 作用 |
| --- | --- | --- |
| `planned_time_s` | 是 | 非负整数计划秒数 |
| `title` | 是 | VoiceRunner Event标题和主要播报动作 |
| `instruction_lines` | 是 | 按行保存现场必要说明，可为空数组但不得含空字符串 |
| `or_refs` | 是 | 该Event提供动作锚点或观察窗口的OR ID列表，可为空数组 |

不增加Vehicle、Round、Session、ECU、Signal、Evidence、状态机、工作流状态或报告字段。Event ID由CANVoiceRunner按脚本顺序生成，中间模型不重复维护。

## 7. 确定性校验

### 7.1 Case契约校验

- 文件存在且为Markdown；
- 存在唯一Case ID、ER表和OR表；
- ER、OR ID不重复；
- 每个OR引用的ER存在。

校验器只检查结构和引用，不评价ER、OR语义质量。

### 7.2 Acquisition Plan校验

- `schema_version`受支持；
- `case_id`与契约一致；
- `events`非空，第一项`planned_time_s`为0；
- 计划时间为非负整数并严格递增；
- `title`非空且不含换行；
- `instruction_lines`均为非空单行字符串；
- `or_refs`引用的OR全部存在；
- 契约中每个OR至少被一个Event引用。

“每个OR至少被引用”只证明存在计划动作或观察窗口，不证明该OR已经获得Evidence。

### 7.3 渲染兼容性校验

CANVoiceRunner当前以`^\s*(\d+)s(?:（[^）]*）)?\s+(.+?)\s*$`识别步骤行，后续非空行合并为详情。Renderer固定输出UTF-8、LF换行、步骤间一个空行，不输出OR引用、JSON字段或解释性标题。

渲染后使用等价规则重新解析并核对Event数量、计划秒数、标题和详情，确保没有详情行被误识别为Event。

## 8. Renderer输出

Renderer只生成VoiceRunner TXT正文：

```text
00s   开始采集
      交流慢充连接、启动、稳定充电及正常退出

20s   开充电小门
      前20秒保持未插枪、无操作
```

Case级现场Script文件名：

```text
L3-<System>-<Module>-<AcquisitionBriefName>_<Module中文名><AcquisitionBriefName中文名>采集.txt
```

例如：

```text
L3-Charge-Slow-FullCycle_慢充全过程采集.txt
```

英文前缀采用Case语义标识；中文后缀由Module中文名、Acquisition Brief Name中文名和“采集”组成，不再使用泛化的`_语音执行脚本`作为Case级输出文件名。

生成阶段不写入Vehicle ID、Round或CANVoiceRunner legacy Session ID。具体TM3实验进入现有采集前三件套时，再按项目既有`TM3-xxx_语音执行脚本.txt`命名规则落位，这不改变Case脚本内容契约。

## 9. 必需与可选输出

必需输出只有：

- VoiceRunner可执行脚本TXT；
- 校验结果：成功，或包含字段路径和原因的失败信息；该结果可以直接输出到命令行，不要求形成附加文件。

仅当Case复杂度或人工审核需要时，才输出Event与OR对应表、Experiment Plan、现场采集记录模板或Acquisition Plan JSON留档。代码不因缺少这些文件拒绝生成Script；项目进入具体TM3实车实验时，仍须遵守当前有效的采集前三件套要求。

## 10. 错误与停止行为

以下情况停止生成并返回错误：

- Case契约尚未审核或无法确认使用的是审核版本；
- Case ID不一致；
- ER/OR表缺失或引用错误；
- 现场条件不足，AI无法安全确定动作；
- Event未覆盖全部OR；
- 时间不递增、字段为空或无法按VoiceRunner格式往返解析。

代码不得通过猜测、补默认动作、删除OR引用或改写文本绕过错误。语义问题返回AI与人工讨论；结构问题修正中间模型后重新校验。

## 11. 两份Reference的验证方式

### 11.1 确定性代码验证

为FullCycle与CurrentControl分别准备符合Acquisition Plan最小模型的固定测试输入，使用同一组读取、校验和渲染函数：

- 不允许按Case ID进入不同代码路径；
- 两个模型均通过契约引用和OR覆盖校验；
- 渲染TXT均能按CANVoiceRunner规则无损往返解析；
- 固定Acquisition Plan的渲染结果可与对应Reference脚本做精确文本回归。

### 11.2 AI与人工语义验证

Reference用于检查观察窗口、现场条件、工作单式语言、内部实现越界和安全可执行性。Reference不得向新Acquisition Plan注入本次Contract、明确现场条件和公共规则未提供的车型、设备或实现细节。AI输出具有措辞差异时，不要求与Reference逐字一致；只有将固定Acquisition Plan交给Renderer时，才要求确定性文本一致。

## 12. 最小实现组织

第一版保持为一个小型Python模块和一组测试，不拆成目录包：

```text
src/tooling/acquisition_plan.py
tests/tooling/test_acquisition_plan.py
```

模块内部只需要：

- `read_case_contract(path)`；
- `load_acquisition_plan(path)`；
- `validate_acquisition_plan(contract, plan)`；
- `render_voice_runner_script(plan)`；
- 一个最小命令行入口。

第一版不拆成`core.py / validator.py / renderer.py`目录包，也不按Case拆成多个生成器。只有代码真实增长并出现稳定边界后，再单独讨论拆分。

## 13. 验收标准

1. FullCycle与CurrentControl使用同一Acquisition Plan模型、校验器和Renderer；
2. 代码中不存在按Case ID生成动作或文案的分支；
3. AI负责Event语义草拟，代码不承担L3推理；
4. Case契约和现场条件职责分离；
5. 输出能被CANVoiceRunner当前ScriptParser解析；
6. 全部OR都有Event引用，但引用不被误称为Evidence；
7. 输出不携带Vehicle、Round或Session业务对象；
8. Candidate Signal、DBC和ASC不进入生成链路；
9. Script为唯一强制业务输出，其他产物按需生成；
10. 未引入数据库、工作流引擎、通用资产索引或多用户抽象。

## 14. 当前不实现

- 自动读取完整L3知识并生成Case；
- 自动审核ER、OR；
- 自动理解任意自然语言现场条件的程序；
- 内置LLM调用、Prompt管理或Agent编排；
- Candidate Signal Mapping或DBC可观测性分析；
- 自动生成Evidence Plan、Evidence Assessment或报告；
- 自动分配Vehicle、Round、Session或TM3实验编号；
- 通用脚本编辑器、GUI、数据库或工作流平台；
- 为尚未出现的系统和异常场景预留抽象层。

## 15. 当前停止点

本设计基线已经人工审核，并按已确认意见完成Acquisition Plan重新定位、核心命名去VoiceRunner化和单文件实现。FullCycle首轮生成结果已完成Human Review并同步为Reference；当前已创建Python模块、严格JSON加载、Case契约结构读取、确定性校验、VoiceRunner渲染、命令行入口及两组Reference回归测试。尚未生成具体Round的正式VoiceRunner脚本。
