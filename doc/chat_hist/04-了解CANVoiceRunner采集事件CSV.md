当前设计“240s只看车侧、320s只看桩侧”对FullCycle来说不够理想。

它可以分别证明：

- 240s车辆显示正在充电；
- 320s小程序显示桩侧正在供电。

但由于相隔80秒，不能稳妥地把两组数值解释为同一个充电状态下的联合观察。如果功率期间发生波动，或者小程序数据存在刷新延迟，就不能用它们支持车侧与桩侧的定量对应关系。

## 更合理的安排

建议保留两个采集点，但不要再按“车侧一次、桩侧一次”分工，而是每个采集点都连续记录车侧和桩侧：

```
240s  记录充电数据1
      拍摄车辆端充电页面
      随即保存微信小程序当前充电页面
      记录小程序页面更新时间；没有更新时间则备注“实时性未知”

320s  记录充电数据2
      再次拍摄车辆端充电页面
      随即保存微信小程序当前充电页面
      记录小程序页面更新时间；没有更新时间则备注“实时性未知”
```

由于两种数据都能在驾驶舱内取得，不需要走动，两个页面可以在很短时间内连续记录。

## 两个采集点各自的目的

### 数据1：充电建立后的联合取证

240s位于扫码启动之后，主要支持：

```
启动请求
→ 桩侧已经形成实际供电
→ 车辆侧已经显示实际充电
→ 两侧现象属于同一次充电建立过程
```

它主要服务ER-03、ER-04和ER-05。

### 数据2：稳定保持阶段的联合取证

320s再次记录同样两类数据，主要支持：

```
第一次充电取证
→ 继续保持充电
→ 第二次仍能观察到桩侧供电和车辆侧充电
```

它主要服务ER-06，并与数据1形成前后对照。

因此两个Event的区别不应是：

```
数据1 = 车侧
数据2 = 桩侧
```

而应是：

```
数据1 = 充电建立后的第一组车侧＋桩侧联合快照
数据2 = 稳定保持后的第二组车侧＋桩侧联合快照
```

## Evidence边界

这种安排能证明两侧现象在同一个短时间窗口内共同存在，但小程序实时性未经确认，所以不能直接宣称：

```
桩侧功率 = 同一瞬间的车辆侧功率
```

合理结论只能是：

- 两侧在同一充电阶段均显示充电成立；
- 数值方向和量级可以交叉检查；
- 若小程序有明确更新时间，才能进一步评估时间接近程度；
- 精确功率对应仍需结合各自时间戳和后续CAN观察。

扫码后对仍亮着的桩屏进行直接拍照仍然有价值，因为它比小程序更接近现场即时读数。它可以作为充电建立阶段的第一份桩侧证据；240s和320s的小程序页面则提供两组便于与车侧页面联合比较的补充证据。

结论：保留240s和320s两个采集点是合理的，但两个点都应采集车侧和桩侧数据。这样既增强L3跨边界验证和持续状态验证，也不增加人员移动或新的Event。
