# Phase 2.6 LLM Semantic Reasoning White-box Contract + Dynamic Validation Design

## 1. Core Decision

**建议进入下一阶段的隔离动态验证实施，但暂不接入正式 Pipeline。**

LLM Semantic Reasoning 应定义为：

> 对程序已经计算并带引用的 Structured Observations 进行 L3 语义映射、证据能力判断、替代解释分析和最小验证设计。

“白盒”指输入、任务、输出、引用和验证过程可审计，不保存模型内部 Chain-of-thought。

- **MUST**：输入和输出结构化；所有关键判断引用输入对象。
- **MUST**：历史人工报告在推理完成前保持隐藏。
- **MUST**：DBC 名称不自动成为已确认物理语义。
- **SHOULD**：允许一次确定性 Follow-up。
- **DEFER**：正式 Pipeline、Evidence Plan 和 Renderer 集成。

## 2. LLM Role

LLM负责：

- 将 Observation 映射到 L3 系统、子系统、状态、变量或控制节点；
- 判断 Observation 能支持哪个 Evidence Requirement；
- 区分事实、程序派生结果和语义推断；
- 提出 Semantic Hypothesis；
- 给出 Alternative Explanation；
- 判断结果是支持、扩展、挑战还是无法映射到当前模型；
- 提出最小 Signal Validation 或下一步计算。

LLM不负责：

- 遍历 ASC；
- 重算 min/max、时序、V×I、积分或相关性；
- 搜索原始 bit；
- 自行创建 Signal 数值；
- 自动确认因果关系；
- 自动提升 Signal Validation 状态；
- 修改 Control Tree。

## 3. Input Contract

建议输入根对象为 semantic_reasoning_input_v1。





```
contract_version package_id package_hash experiment_context l3_context event_anchors[] observations[] candidates[] consistency_results[] validation_states[] allowed_follow_up_operations[]
```

### experiment_context — MUST





```
experiment_id experiment_goal purpose system_boundary vehicle_context collection_conditions[] analysis_mode planned_actions[] known_limitations[] source_artifacts[]
```

analysis_mode 枚举：





```
STATIC EVENT_DRIVEN
```

### 时间类型 — MUST

所有时间对象必须明确标记：





```
PLANNED_TIME OBSERVED_EVENT_TIME CAN_OBSERVED_TIME
```

不得仅提供一个含义模糊的 time_s。

### event_anchors[] — MUST for dynamic validation





```
event_id event_type time_type time_s source uncertainty_s description raw_refs[]
```

事件来源枚举：





```
EXTERNAL_OBSERVATION HUMAN_TIMESTAMP CAN_OBSERVED_INPUT CAN_OBSERVED_STATE PLANNED_ONLY
```

PLANNED_ONLY 只能用于窗口定位，不能用于时延或因果计算。

### observations[] — MUST





```
observation_id observation_class signal_ref bus_key dbc_source definition_fingerprint semantic_status observed_summary deterministic_metrics raw_refs[] quality_flags[]
```

observation_class：





```
DIRECTLY_OBSERVED DETERMINISTICALLY_DERIVED CONTRADICTORY UNRESOLVED
```

### candidates[] — MUST

沿用 Phase 2.5 Candidate 主体字段：





```
candidate_id source_space target pattern_type observed_summary metrics event_refs[] observation_refs[] raw_refs[] quality_flags[]
```

### consistency_results[] — SHOULD

用于承载程序计算的物理闭环、顺序或冲突：





```
relation_id relation_type input_refs[] deterministic_result tolerance status raw_refs[]
```

LLM不得自行重算这些关系。

## 4. L3 Context Contract

单次推理不输入完整 L3 文档。输入内容限定为：

- 实验声明的系统边界；
- 对应系统和子系统定义；
- 当前实验涉及的 Control Mainline 片段；
- 相关 Control Tree 节点及其稳定ID；
- 状态、变量和 Implementation 引用；
- 当前 Evidence Requirements；
- 已知语义不确定性。

建议结构：





```
context_scope systems[] control_mainline_refs[] control_tree_nodes[] state_definitions[] variable_definitions[] evidence_requirements[] known_uncertainties[] reference_documents[]
```

每个 Control Tree Node 和 Evidence Requirement 必须具有稳定ID，例如：





```
CT_DRIVE_GEAR_REQUEST CT_DRIVE_GEAR_FEEDBACK CT_DRIVE_ENABLE_STATE ER_GEAR_REQUEST_ACCEPTANCE
```

- **MUST**：L3 Context 根据实验目的和预先声明的系统边界选择，不能根据“已经发现了哪些Signal”反向裁剪。
- **MUST**：保留 NO_SAFE_MAPPING 和 OUTSIDE_CURRENT_SCOPE。
- **MUST**：明确声明 L3 是 Semantic Prior，不是 Observation Whitelist。
- **SHOULD**：只带当前节点、必要祖先及直接相邻节点。
- **DEFER**：自动从完整 Control Tree 编译上下文。

## 5. Semantic Reasoning Tasks

第一版显式执行八项任务：

1. **Observation Classification**
   确认输入属于直接观测、程序派生、矛盾或未解决。

2. **L3 Domain Mapping**
   映射系统、子系统、状态、变量或 Implementation。

3. **Control Tree Mapping**
   映射实际存在的 Control Tree Node；允许 NO_SAFE_MAPPING。

4. **Evidence Requirement Mapping**
   枚举为：

   

   

   `DIRECT_SUPPORT PARTIAL_SUPPORT CONTRADICTION UNRELATED INSUFFICIENT`

5. **Relationship Hypothesis**
   描述 request/actual、state transition、feedback、proxy、companion或物理闭环候选。

6. **Alternative Explanation**
   对相关性、未知bit、DBC冲突和控制关系推断提出竞争解释。

7. **Model Interaction**

   

   

   `SUPPORTS_CURRENT_MODEL EXTENDS_CURRENT_MODEL CHALLENGES_CURRENT_MODEL OUTSIDE_CURRENT_MODEL INSUFFICIENT_TO_MAP`

8. **Validation Need**
   给出最小确定性计算、Signal Validation、外部证据或补采要求。

## 6. Output Contract

建议输出根对象为：





```
contract_version result_id input_package_id input_package_hash overall_status findings[] validation_requests[] audit_metadata
```

每个 finding：





```
finding_id candidate_refs[] observation_refs[] relation_refs[] event_refs[] fact_bindings[] l3_domain_mapping control_tree_mapping evidence_requirement_mapping relationship_kind causality_status semantic_hypothesis alternative_explanations[] model_interaction supported_claims[] unsupported_claims[] missing_evidence[] signal_validation_needed minimum_next_check uncertainty confidence trace_refs[]
```

### 字段级要求

- **MUST**：引用、分类、Mapping、Hypothesis、Alternative、Evidence Gap、最小检查。
- **SHOULD**：支持和不支持的 Claim 分开。
- **SHOULD**：confidence 使用 LOW/MEDIUM/HIGH，避免伪精确百分数。
- **DEFER**：复杂 Candidate Graph、自动 Promotion Lifecycle。

自然语言只允许出现在：

- semantic_hypothesis
- alternative_explanations.description
- Claim说明
- Evidence Gap说明
- Validation Proposal说明

ID、状态、映射结果和因果状态必须枚举化。

## 7. Traceability Rules

以下对象必须引用真实输入ID：

- Observation 和 Candidate 解释；
- L3 Domain Mapping；
- Control Tree Mapping；
- Evidence Requirement Mapping；
- Supported Claim；
- Contradiction；
- Validation Request；
- Targeted Follow-up。

引用链至少达到：





```
Semantic Finding → Observation/Candidate/Relation → Signal或Raw Candidate → ASC时间及原始帧
```

DBC Signal 还必须能够回溯：





```
Signal Ref → DBC source → definition fingerprint → bus key
```

## 8. Program-side Validation Rules

程序必须拒绝：

- 不存在的 Candidate、Observation、Event或Relation ID；
- 不存在的 Control Tree Node、Evidence Requirement；
- DIRECTLY_OBSERVED 引用了派生或推断对象；
- LLM自由生成新的数值统计；
- CONTRADICTORY 少于两个冲突输入；
- DIRECT_SUPPORT 没有 Observation或Relation引用；
- 未验证DBC Signal被标记为确认物理语义；
- PLANNED_ONLY 被用于计算响应时延；
- CAN状态边沿被改写为人工操作时刻；
- 相邻时间变化被标记为已确认因果；
- Follow-up请求引用输入包之外的对象；
- 超过一次 Follow-up。

程序还应验证：

- Input hash与结果声明一致；
- 所有Raw Ref落在ASC时间范围内；
- Bus Key、DLC和Signal Ref一致；
- 输出枚举值合法；
- NO_SAFE_MAPPING不附带虚构节点。

## 9. Observed / Derived / Inferred Model

严格采用三层：

| 类型                      | 来源                               | LLM权限                                    |
| ------------------------- | ---------------------------------- | ------------------------------------------ |
| DIRECTLY_OBSERVED         | 原始帧、解码值、外部事件记录       | 只能引用                                   |
| DETERMINISTICALLY_DERIVED | 程序计算的统计、顺序、闭环、重复性 | 只能引用和解释                             |
| SEMANTICALLY_INFERRED     | L3映射、角色判断、关系假设         | 可以生成，但必须带引用、替代解释和不确定性 |

LLM不能把推断重新包装为 Observation。

建议每个Claim强制携带：





```
claim_class support_refs[]
```

其中 claim_class：





```
OBSERVED DERIVED INFERRED UNSUPPORTED
```

## 10. 防止 Time-order → Causality

第一版不允许输出 CAUSALITY_CONFIRMED。

causality_status只允许：





```
TEMPORAL_ASSOCIATION_ONLY CONTROL_RELATION_SUPPORTED CAUSALITY_NOT_ESTABLISHED NOT_APPLICABLE
```

即使发现：





```
请求Signal → 挡位反馈 → ENABLE
```

也只能说明控制关系获得支持。除非未来具有受控干预、重复实验、反例和替代解释排除机制，否则不能写成已经证明ECU内部因果算法。

## 11. Alternative Explanation Model

以下情况至少需要一个 Alternative Explanation：

- Event proximity；
- Unknown/Residual Candidate；
- DBC语义冲突；
- Proxy/companion判断；
- Control Tree映射；
- 任何 SEMANTICALLY_INFERRED Claim。

最小结构：





```
alternative_id description compatible_observation_refs[] discriminating_evidence minimum_check
```

例如挡位请求附近出现Unknown bit时，至少保留：

- 换挡请求相关状态；
- 报文计数器或分页字段；
- 伴随网络状态；
- 同一报文内其他状态变化。

## 12. Evidence Gap Model





```
gap_id blocked_claim missing_evidence_type reason minimum_evidence_needed priority
```

missing_evidence_type枚举：





```
EXTERNAL_EVENT_TIME DIRECT_REQUEST CONDITION_OR_PERMISSION EXECUTION_FEEDBACK PHYSICAL_MEASUREMENT SIGNAL_VALIDATION REPEAT_OBSERVATION ALTERNATIVE_CONDITION DBC_DEFINITION
```

Evidence Gap必须说明它阻止提升哪个Claim，而不是罗列泛化免责声明。

## 13. Targeted Follow-up Protocol

建议允许：





```
1次 Initial Reasoning + 最多1次 Targeted Deterministic Follow-up + 1次结果更新
```

Follow-up请求：





```
request_id operation input_refs[] parameters expected_decision
```

第一版允许的操作：

- 指定窗口统计；
- 重复事件一致性；
- Event前后状态分布；
- Transition顺序及时间差；
- 原始帧摘取；
- 已知Signal与Residual Candidate同步性；
- DBC定义并列解码；
- 已定义物理闭环重算。

程序返回：





```
request_id calculation_id method parameters result raw_refs[] limitations[]
```

LLM不能发起任意代码、全量相关性或开放式ASC搜索。第二轮之后必须停止。

## 15. Recommended Validation Sample

推荐：

> **TM3-003 静止挂挡**

理由：

- 具有D、R、P多个重复闭环；
- Request、实际挡位和电驱状态属于不同控制角色；
- 状态顺序清晰；
- 车辆保持静止，减少道路、坡度、负载和能量流干扰；
- 第一次D挡存在提前松制动偏差，可测试LLM是否保留替代解释；
- 存在Unknown Candidate，可测试相关性是否被错误命名；
- 历史报告提供详细Hidden Comparison；
- 实施成本最低。

关键时间边界：

- SCCM请求边沿属于 CAN_OBSERVED_INPUT；
- DI_gear和DI_systemState属于 CAN_OBSERVED_STATE；
- 脚本中的25/55/85/115秒属于 PLANNED_TIME；
- 缺少独立人工Observed Event Time。

因此本验证可以评价“CAN内部请求—反馈—状态链”，不能评价“驾驶员实际拨杆动作到CAN请求”的物理时延。

参考材料：

- TM3-003采集脚本
- TM3-003历史分析结论
- TM3-003原始ASC

历史分析结论只能在Reasoning完成后用于对照。

## 16. Dynamic Validation Data Flow





```
TM3-003 ASC + DBC        ↓ ID Aggregation / Coverage / Signal Summary        ↓ CAN_OBSERVED_INPUT与状态转换提取        ↓ Known + Residual + Unknown Candidate        ↓ Reasoning Input Contract + TM3-003 L3片段        ↓ Initial LLM Semantic Result        ↓ Program-side Reference/Type/Time Validation        ↓ 最多一次 Targeted Deterministic Follow-up        ↓ Updated Semantic Result        ↓ Audit Record        ↓ 解封TM3-003历史报告并做后验对照
```

## 17. Acceptance Criteria

### MUST

- 只引用真实存在的输入对象；
- 至少正确映射拨杆请求、实际挡位和电驱状态中的部分对象；
- 对Unknown/Residual Candidate允许 NO_SAFE_MAPPING；
- Observed、Derived和Inferred严格分开；
- 不把计划时间写成实际操作时间；
- 不把CAN请求边沿写成人工拨杆动作时刻；
- 不把请求先于反馈自动升级为已确认内部因果；
- 至少为关键控制关系提供一个Alternative Explanation；
- 明确缺少独立人工事件时间；
- 提出一个可执行的最小Follow-up；
- 推理前不读取TM3-003历史结论；
- 输出通过程序引用和枚举校验；
- 推理完成后才进行Hidden Comparison。

### SHOULD

- 区分Request、实际状态反馈和系统状态；
- 识别重复D/R/P闭环；
- 正确处理第一次D挡提前松制动的偏差；
- 识别可能的companion/proxy Candidate；
- 指出哪些控制条件没有直接观测；
- 对无法解释的Unknown Candidate保持未命名。

## 18. Future No-DBC Compatibility

Contract必须允许：

- signal_name=null；
- dbc_source=null；
- semantic_status=UNKNOWN；
- Target使用 frame/byte/bit；
- 仅凭Raw Ref和Event关联生成Hypothesis；
- Model 3已验证语义作为 comparison_reference；
- 跨车型映射结果只能是 SEMANTICALLY_INFERRED；
- 不允许把Tesla编码、CAN ID或bit位置直接迁移到其他车型。

本轮不实现跨车型分析。
