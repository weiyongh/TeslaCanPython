# 采集身份与追溯约定

**文档性质：** 项目级方法约定  
**形成日期：** 2026-09-10  
**最新修订：** 2026-09-11
**审核状态：** 已审核通过  

## 1. Minimum Case Contract边界

当前合同只服务于TeslaCanPython的单车、单人、人工审核工作流，不扩展为通用LIMS或实验管理平台。

统一业务关系为：

```text
Case
→ Vehicle
→ Round
→ Evidence
```

TeslaCanPython不定义独立Session领域对象。ASC文件、分析运行和导出批次也不得称为Session。

## 2. Experiment Plan与采集脚本

Experiment Plan是语义根，定义：

- 实验目的与适用范围；
- L3控制关系和状态机；
- Evidence Requirements；
- 有效、无效、终止和完成判据；
- 必要的车内、人工事件及外部物理证据。

采集脚本是现场执行与Event追溯的操作根。脚本必须由已明确的Experiment Plan生成，不能反向承担完整实验语义，也不能用简化TTS文本替代Evidence设计。

## 3. Case

Case由L3验证需求产生，表达“为什么采、验证什么”，不由车型产生。

格式：

```text
L3-<System>-<Object>-<Topic>
```

慢充候选示例：

```text
L3-Charge-Slow-FullCycle
L3-Charge-Slow-Permission
L3-Charge-Slow-CurrentControl
L3-Charge-Slow-ThermalStability
L3-Charge-Slow-AutoStop
```

同一Case可以在不同Vehicle上进行车型实例化，核心L3验证问题原则上保持一致。

## 4. Vehicle

Vehicle ID表示车型技术版本边界，格式为：

```text
MANUFACTURER-MODEL-TECH_VERSION
```

规则：

1. 固定为三段，段之间使用连字符（`-`）。
2. 连字符不得出现在任何段内部。
3. 当前M3使用`TESLA-M3-SOP5`。
4. 生产日期、电池、供应商、软件版本、SOC、温度和环境等信息属于Round Metadata，不写入Vehicle ID。

### 4.1 Round输入目录的车型标记

实车采集导入TeslaCanPython后，每个Round输入目录使用一个无后缀空文件声明Vehicle ID。文件名就是Vehicle ID，文件内容为空，例如：

```text
<Round输入目录>/
├── TESLA-M3-SOP5
├── session.json
├── event_timeline.csv
├── photos/
└── can/
```

该文件是TeslaCanPython采集分析工作流程中约定俗成的车型标记（Vehicle Marker），不属于VoiceRunner原始导出字段。规则如下：

1. 一个Round输入目录只能有一个Vehicle Marker。
2. 分析开始时先读取Vehicle Marker，再绑定`session.json`、`event_timeline.csv`、照片、备注和ASC。
3. 不得从目录名、DBC文件名、CAN Signal、历史采集或项目记忆推断Vehicle ID来替代该标记。
4. Vehicle Marker缺失、格式无效或同目录出现多个时，必须将车型身份标记为未解决，不得静默选择。
5. 该标记只声明Vehicle ID；生产日期、软件版本、SOC、温度和环境等仍由Round Metadata记录。

## 5. Round

Round是同一`Case + Vehicle`下的一次独立实车验证轮次。

以下情况均创建新Round：

- 首次执行某个Case；
- 采集后分析发现问题，重新采集；
- 现场完成后发现漏拍、动作偏差或数据问题，当场再次执行；
- 不同季节、环境或其他实验条件下重新验证；
- 其他准备独立评价Evidence完整性和结果的再次执行。

Round之间必须独立保存和评价，不能覆盖、替换或静默混合。跨Round比较或联合引用时，必须明确每条Evidence的来源Round及其条件。

## 6. CANVoiceRunner legacy Session映射

CANVoiceRunner当前内部称为Session的一次`Start → Stop`，在TeslaCanPython业务语义中对应一个Round。

```text
CANVoiceRunner Session
→ TeslaCanPython Round
```

因此：

- VoiceRunner的`session_id`、`session.json`和Session目录名属于legacy实现细节；
- 读取原始字段时保持原名，但进入TeslaCanPython边界后统一映射为Round；
- TeslaCanPython不因legacy字段名创建或解释独立Session；
- 点击结束后该Round完成；如需重新执行，VoiceRunner创建新的legacy Session，业务上形成新的Round。

## 7. VoiceRunner输出的Evidence入口

一个Round的VoiceRunner原始采集包至少可能包含：

- `event_timeline.csv`：Event计划时间、实际触发时间、跳过时间和状态；
- `session.json`：legacy Session元数据、完整Event描述、照片、备注和录音元数据；
- 照片：车机、充电设施、诊断工具或现场状态的外部物理证据；
- 备注：实际动作、偏差、读数、异常和照片解释；
- 录音：当前由用户人工处理，处理规范确定前不由TeslaCanPython主动转写或解释。

`event_timeline.csv`与`session.json`必须来自同一VoiceRunner导出目录，并作为同一Round读取。照片与备注通过显式ID和各自时间字段关联，不能按目录顺序或文件名猜测。

### 7.1 VoiceRunner输入合同入口

TeslaCanPython读取VoiceRunner采集结果时，不通过全仓搜索选择说明文档，统一使用以下当前有效合同：

| 输入物 | 当前版本识别 | 权威说明文档 |
|---|---|---|
| `session.json` | `schema_version = 1` | `android/CANVoiceRunner/doc/V2优化/任务7/任务7_结构化导出_schema_v1_说明.md` |
| `session.json`机器校验合同 | JSON Schema Draft 2020-12 | `android/CANVoiceRunner/doc/V2优化/任务7/任务7_结构化导出_schema_v1.json` |
| `event_timeline.csv` | 同目录JSON的`schema_version = 1`与v1固定表头 | `android/CANVoiceRunner/doc/V2优化/任务7/event_timeline_csv_v1_接口合同.md` |

JSON说明文档负责字段语义、对象关系和Schema校验边界；JSON Schema是机器校验的唯一合同；CSV接口合同负责固定表头、字段、状态、时间重算以及与ASC分析端的交接关系。VoiceRunner总体设计、Mock和实现测试记录属于背景或验证材料，不作为日常采集分析选择输入合同的入口。

首次接入或发现`schema_version`、CSV表头、字段结构或VoiceRunner输出版本变化时，重新读取并审核对应合同；同版本日常采集不重复扫描或通读这些稳定文档。

### 7.2 采集完成后的统一三阶段流程

采集结果从确认到分析统一使用以下术语和顺序：

```text
Acquisition Package
        ↓
Validation      原始采集包校验
        ↓
Recognition     采集信息识别 / Event关联
        ↓
Analysis        CAN / Signal / Evidence分析
```

#### Acquisition Package / 原始采集包

指一个Round导入分析端时的完整原始输入，包括Vehicle Marker、VoiceRunner的`session.json`和`event_timeline.csv`、实际存在的照片、Note、录音，以及一个或多个ASC。

#### Validation / 原始采集包校验

只做通用的包级规范巡检：确认必要文件存在、可读、身份明确，并提取VoiceRunner与一个或多个ASC的基本起止和时长信息。这里不解析CAN报文Payload，不进行DBC解码、Signal统计、Event覆盖分析或Evidence判断。

VoiceRunner作为可信任采集端：首次接入或VoiceRunner、JSON Schema、CSV合同发生版本变更时进行深度校验；同版本后续采集只做上述轻量校验，不每次重复验证VoiceRunner内部已验证的生成逻辑。

#### Recognition / 采集信息识别 / Event关联

只做通用的采集信息识别：读取Vehicle、Round、实际Event时间和状态；按`session.json`已有的ID关系读取Event关联的照片、Note和录音，将其中可见、可读或可听的现场信息归纳为采集事实。Recognition不读取CAN报文内容，不进行DBC解码、Signal分析、控制关系推理或Evidence Assessment。

没有审核UI时，Recognition先将解析结果和AI原始识别值持久化为`acquisition_context_toreview.json`，再输出可读的`recog_values_review.md`作为人工审核界面，避免后续步骤反复解析原始采集包。文档显示采集中文名，并按`Round → Event → Resource → Value`组织；图片使用`![img](url)`直接预览，Value以表格保留来源位置、AI原始识别值、人工确认值、审核状态和备注。人工完成校对、补充并明确审核通过后，再将待审上下文与审核结果合成为正式`acquisition_context.json`。待审JSON是处理快照，Markdown是审核界面，审核后的JSON才是Analysis使用的正式机器输入，三者不得形成并行真值。

#### Analysis / CAN / Signal / Evidence分析

在Validation记录的ASC基本时间信息和Recognition形成的现场事实、Event锚点上，才开始读取CAN报文Payload，进行ASC解析、DBC解码、CAN ID与Signal统计、Event窗口计算、控制关系和Evidence分析。Validation和Recognition不替代Evidence Plan、人工审核、Evidence Assessment或最终结论。

## 8. 时间与追溯原则

必须区分：

```text
Planned Time
≠ VoiceRunner Event Time
≠ Photo/Note Time
≠ CAN Observed Time
```

VoiceRunner Event提供独立现场锚点；分析观察ASC在其前后如何响应。不得用CAN变化反推人工动作，再用该动作时间循环证明CAN响应。

最终应能进行以下反向追溯：

```text
Conclusion
→ Evidence Assessment
→ Evidence
→ Event / Photo / Note / ASC Window
→ Round
→ Vehicle
→ Case
→ Evidence Requirement / L3验证需求
```

## 9. DBC边界

DBC用于车型实例化阶段的候选解析与Signal Validation：

```text
L3验证需求
→ Case与Evidence Requirements
→ DBC候选解析
→ 实车Signal Validation
```

不得按照Signal名称或当前DBC覆盖反向设计Case；也不得因为字段可解码或与Event同时变化，就把它升级为已确认语义或正式Evidence。

第三方DBC Signal在完成定义审计、实测时序、方向、物理闭环及必要独立证据验证前，只能作为候选Signal。
