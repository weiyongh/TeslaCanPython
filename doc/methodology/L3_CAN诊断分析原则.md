## 1. 总体判断

这次 Codex 真正的问题不是“算错了”，而是**分析层级没有收住**。

数据挖得很细，边界条件也写得很谨慎，但没有围绕这次实验的三个诊断问题形成一个清晰的“控制链结论”；尤其到了制动踏板这一段，把“观察到了什么”和“控制逻辑意味着什么”混在了一起。

这次实验真正要验证的是：

**电门 → 请求扭矩 → 实际扭矩 → 轴速/车速 → 电驱功率 → Pack 放电**

核心回答三个问题：

1. 请求增加后，实际扭矩能否跟随？
2. 扭矩执行后，车辆运动和电池输出是否相互对应？
3. 两次表现不同，是驾驶操作不同，还是控制链某一环节没有跟上？

现有报告虽然把答案散落在很多地方，却没有把它们组合成清晰的诊断结论。

---

## 2. 第一个问题：请求增加后，实际扭矩能否跟随？

**答案：能，而且跟随相当明确。**

第一次：

- 峰值踏板：25.6%
- 请求扭矩：684 Nm
- 实际扭矩：710 Nm

第二次：

- 峰值踏板：21.2%
- 请求扭矩：554 Nm
- 实际扭矩：558 Nm

更重要的不是峰值，而是无制动正驱动样本：

- 第一次平均绝对差：约 1.26 Nm
- 第二次平均绝对差：约 2.16 Nm
- 实际−请求平均分别只有约 +0.25 / +0.34 Nm

所以这里完全可以写成：

> **在本次中等负载正驱动工况下，请求扭矩建立后，实际扭矩能够同步跟随，未观察到持续性请求—执行偏离。后电驱扭矩执行链表现正常。**

Codex 当前写法类似：

> “数值支持本次请求与实际趋势跟随，但不是厂家合格阈值……”

这种写法当然严谨，但读完以后人的第一感觉反而是：**到底正常不正常？**

诊断报告不能只有免责声明。

我们当然不能写“车辆绝对无故障”，但完全可以写：

> **本次采集范围内未发现扭矩执行异常。**

这已经足够明确。

---

## 3. 第二个问题：扭矩执行后，车辆运动和能源输出有没有跟上？

这一部分的证据其实非常完整。

数据已经显示：

**踩电门后 → 请求/实际扭矩上升 → 轴速和车速上升 → 电驱功率增加 → Pack 正电流增加**

而且第一次驾驶输入更大：

- 25.6% 踏板
- 684 / 710 Nm 请求/实际扭矩
- 13.5 kW 电驱功率
- 41 A Pack 电流
- 14.112 kW Pack 功率

第二次驾驶输入较小：

- 21.2% 踏板
- 554 / 558 Nm 请求/实际扭矩
- 9.0 kW 电驱功率
- 28.1 A Pack 电流
- 9.706 kW Pack 功率

这不是简单的“几个变量都变了”，而是已经构成了一条很有价值的因果顺序证据链：

**驾驶输入较强  
→ 请求扭矩较大  
→ 实际扭矩较大  
→ 电驱输出较大  
→ Pack 放电电流/功率较大**

车辆速度也随之提高。

因此第二个问题可以直接回答：

> **是。两次加速均观察到扭矩执行、车辆运动和电池放电方向一致，控制链和能源链相互对应，没有出现“扭矩已经执行而车辆不响应”或“车辆加速但电池输出没有相应增加”的脱节。**

这才是这次采集真正有价值的地方。

---

## 4. 第三个问题：两次表现不同，主要来自驾驶操作还是控制链异常？

这里其实已经有比较强的证据。

| 指标 | 第一次 | 第二次 |
|---|---:|---:|
| 踏板峰值 | 25.6% | 21.2% |
| 请求扭矩 | 684 Nm | 554 Nm |
| 实际扭矩 | 710 Nm | 558 Nm |
| 电驱功率 | 13.5 kW | 9.0 kW |
| Pack 电流 | 41.0 A | 28.1 A |

所有变量都沿着**同一个方向**变化。

所以第三问可以明确回答：

> **两次表现差异首先可以由驾驶输入强度差异解释，目前没有证据指向控制链某一级没有跟上。**

这句话非常重要。

它不是：

> “证明车辆绝对没有故障。”

而是：

> **“这次两次数据差异，无需调用故障解释。”**

这是诊断推理中非常关键的一步。

## 5. 制动分析为什么显得含糊

这里是 Codex 当前最重要的技术问题之一。

报告发现 98～100 秒低速补踩制动时：

- 扭矩仍为正
- 请求与实际动态差值较大
- 同帧平均绝对差约 35.37 Nm
- 最大约 68 Nm

随后总结成类似：

> “踩刹车后，电驱扭矩不一定变负……”

这句话从**观察事实**来说没有错，但作为**控制逻辑解释**还不够。

因为这里至少存在三个不同层级：

### 驾驶员原始输入

- 电门位置
- 制动踏板 / iBooster 输入杆

↓

### 整车扭矩仲裁

可能包括：

- 驾驶需求
- 蠕行需求
- 回收制动
- 制动优先
- TCS / ESP
- 挡位
- 车速状态
- 其他车辆控制状态

↓

### 最终电驱请求

`DI_torqueRequest`

↓

### 电机实际执行

`DI_torqueActual`

Codex 当前分析容易把：

**制动踏板 → torqueRequest**

当成一个直接关系。

但实际更可能是：

> **制动输入进入上游扭矩仲裁，而 torqueRequest 已经是仲裁后的结果之一。**

这两者不是同一层级。

## 6. 98～100 秒“踩着刹车仍然正扭矩”并不一定异常

这一段更合理的分析问题应该是：

> **车辆处于低速蠕行状态时，驾驶员施加制动以后，正驱动请求如何被抑制、保持或撤销？**

因为数据已经发现：

**D 挡 + 电门 0 + 松刹车  
→ 正扭矩请求  
→ 车辆低速运动**

这符合蠕行/低速驱动特征。

因此 98～100 秒：

**D 挡 + 电门 0 + 正扭矩请求 + 踩制动**

本身并不奇怪。

这时候完全可能出现：

**电驱仍维持一定正向蠕行扭矩**

同时：

**液压/摩擦制动产生反向制动力**

车辆因此被制动或保持低速。

也就是说：

> **正驱动扭矩与脚刹制动力可以同时存在。**

所以“踩刹车以后扭矩为什么没有马上变成负值”本身，并不能说明请求异常。

---

## 7. “请求—实际差 35 Nm”也不能简单解释为制动影响了扭矩执行

这是 Codex 当前另一个明显不足。

它把：

- 无制动时 MAE 约 1～2 Nm
- 制动时 MAE 约 35 Nm

直接放在一起比较。

这当然值得记录，但不能马上解释为：

> **制动使实际扭矩不再跟随请求。**

原因是：

- 扭矩报文约 100 ms 周期
- 制动、踏板、车速等报文周期不同
- 98～100 秒本身是极低速瞬态窗口
- 制动输入正在变化
- 正蠕行扭矩仍存在
- 车辆接近停住
- 多个控制状态可能切换

这是一个典型的**瞬态仲裁窗口**。

正确分析顺序应该是：

**请求什么时候变？**

↓

**实际什么时候变？**

↓

**差值是持续偏差还是边沿瞬态？**

↓

**稳定以后是否重新收敛？**

而不是拿整个窗口的 MAE 直接和稳态正驱动相比。

> **35 Nm 这个数字本身不是核心，差值的时间结构才是核心。**

这是程序下一版最值得改进的地方之一。

---

## 8. 制动部分真正应该分析的是时序关系

以后程序不要只输出：

> 平均绝对差 35 Nm，最大 68 Nm。

而应该针对制动事件自动对齐以下变量：

1. `IBST_sInputRodDriver` —— iBooster 输入杆行程
2. `IBST_driverBrakeApply` —— 制动施加状态
3. Accelerator pedal —— 电门
4. `DI_torqueRequest` —— 电驱请求扭矩
5. `DI_torqueActual` —— 电驱实际扭矩
6. Vehicle speed —— 车速

最好形成事件窗口曲线或逐时间序列表。

真正要回答的是：

> **刹车开始以后，请求扭矩发生了什么？**

可能出现的情况包括：

### A. 正请求逐渐下降但保持正值

可以理解为蠕行扭矩被削弱。

### B. 正请求降到 0

意味着正驱动请求被撤销。

### C. 请求进入负值

说明进入电驱回收制动。

### D. 请求仍保持正值，但车速下降

说明车辆减速不能由电驱负扭矩解释，脚刹机械/液压制动力很可能已经在起作用。

这才是真正意义上的：

> **制动踏板对扭矩请求的影响分析。**

## 9. 术语和控制层级必须严格分开

以后分析程序最好强制区分：

### Accelerator Pedal

驾驶员电门输入。

### Brake Input

驾驶员制动输入。

### Torque Request

整车控制经过仲裁以后给电驱的扭矩请求。

### Torque Actual

电驱实际执行扭矩。

不要简单写成：

> “踏板请求 → 请求扭矩”

特别是在制动工况下，这种表达容易造成控制逻辑混乱。

**Torque Request 不等于 Accelerator Request。**

这个区别对于后续建立控制树非常重要。

更加准确的控制层级应该是：

**驾驶员输入层**

电门 / 制动

↓

**车辆状态与仲裁层**

D/R 挡  
车速  
蠕行  
制动状态  
回收策略  
ESP / TCS  
其他约束

↓

**扭矩请求**

↓

**电驱执行**

↓

**车辆运动**

↓

**能源响应**

这次数据实际上很好地把这个区别暴露了出来。

## 10. 建议重写本次报告的“诊断总结”

建议 Codex 后续把本次 TM3-009 的最终总结压缩成以下形式：

> **本次 TM3-009 中等负载加速采集验证了后电驱动力控制链的动态对应关系。**
>
> 两次加速过程中，电门增加后请求扭矩明显上升，实际扭矩同步跟随；无制动正驱动样本中，请求与实际扭矩平均绝对差分别约 1.26 Nm 和 2.16 Nm，未观察到持续性扭矩执行偏离。
>
> 扭矩执行后，轴速/车速随之上升，电驱功率以及 Pack 放电电流、功率同步增加，说明“驾驶输入 → 扭矩请求 → 扭矩执行 → 车辆运动 → 电驱功率 → 电池放电”在本次工况下形成一致响应。
>
> 第一次加速的电门、请求扭矩、实际扭矩、电驱功率和 Pack 放电均明显高于第二次，变量变化方向一致，因此两次表现差异首先可由驾驶输入强度不同解释，目前没有证据表明动力控制链某一级未跟随。
>
> 第二次起步前 98～100 秒的补踩制动属于不同控制工况。此时车辆处于低速、零电门及蠕行正扭矩背景下，制动输入与正驱动扭矩可以同时存在，因此不能以“踩刹车后扭矩仍为正”判断异常。该窗口应单独用于研究**制动输入—扭矩仲裁—蠕行驱动**关系，而不应并入本次正驱动扭矩跟随评价。
>
> **本次三个诊断问题的回答：**
>
> 1. **请求扭矩增加后，实际扭矩能够跟随：是。**
> 2. **扭矩执行后，车辆运动与电池输出相互对应：是。**
> 3. **两次差异主要来自驾驶操作还是控制链异常：现有证据支持驾驶输入不同，未发现控制链未跟随。**

## 11. 对 Codex 分析程序的总体改进方向

Codex 当前已经很会“谨慎”。

下一阶段不是继续增加谨慎，而是增加**判断能力**。

“尚无厂家阈值”“不能证明”“待验证”这些边界仍然需要保留，但不能成为最终结论的主体。

以后自动分析程序建议固定采用四层输出：

### 第一层：事实

实际发生了什么？

例如：

- 电门变化
- 请求扭矩变化
- 实际扭矩变化
- 轴速/车速变化
- Pack 电流变化

### 第二层：控制关系

这些变量之间是否按照预期控制链方向对应？

例如：

**电门↑ → 请求扭矩↑ → 实际扭矩↑ → 车速↑ → Pack 放电↑**

### 第三层：诊断判断

直接回答本次实验问题。

例如：

> **本次采集范围内未发现后电驱扭矩请求—执行链异常。**

或者：

> **两次表现差异可由驾驶输入不同解释，无需调用控制链故障假设。**

### 第四层：证据边界

最后再说明：

- DBC 来源与适配限制
- 缺少厂家阈值
- 哪些变量没有采到
- 哪些结论不能外推

也就是始终坚持：

> **事实 → 控制关系 → 诊断判断 → 证据边界**

这才会逐渐成为 L3 故障诊断分析程序，而不只是一个很勤快的 CAN 数据统计程序。
