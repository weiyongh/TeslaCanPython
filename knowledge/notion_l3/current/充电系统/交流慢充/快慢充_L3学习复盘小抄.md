# 快慢充_L3学习复盘小抄

# 快慢充 L3 学习复盘小抄
> **复盘目的**
	不再重复快充、慢充的具体知识点，而是提炼这轮学习后形成的共同诊断骨架与<br>L3 方法论。
	**到这里收敛，不继续摆”满汉全席”。**
---
## 1. 快慢充共同的诊断骨架
### 1.1 共同生命周期
```plain text
充电口
↓
充电允许
↓
充电建立
↓
充电过程
↓
充电结束
```
它回答的是充电系统最基本的五个问题：
```plain text
充电口
→ 车与外部能源系统的连接是否成立？

充电允许
→ 双方条件是否允许进入能量传输？

充电建立
→ 功率路径与充电电流是否真正建立？

充电过程
→ 已建立的充电能否持续、正确、受控运行？

充电结束
→ 如何停止功率传输并安全退出？
```
这是一层高于具体车型、具体 ECU 和具体快慢充实现的**生命周期骨架**。
---
### 1.2 国标协议 / 接口机制
生命周期骨架相同，但快慢充用不同方式表达车桩状态、能力和控制意图。
```plain text
                 充电生命周期
                       │
        ┌──────────────┴──────────────┐
        │                             │
      慢充                          快充
        │                             │
 CC / CP / PWM / S2          硬线 + 数字通信协议
        │                             │
        └──────────→ Evidence ←───────┘
```
因此：
> **生命周期告诉我们”事情走到了哪一步”；国标协议 /<br>接口机制提供车桩之间状态交互和证明这些状态的 Evidence。**
慢充的关键 Evidence 更集中于 CC、CP、PWM、S2 等接口机制及车辆内部状态。
快充的控制链跨越车桩边界，很多关键 Evidence<br>需要通过车桩数字通信协议恢复。
---
### 1.3 共有系统边界
快慢充虽然功率转换位置不同，但都受到一组车辆边界系统持续约束：
```plain text
BMS / Pack
高压安全
HVIL / IMD
HV Bus
接触器 / 预充
热管理
低压供电
整车状态
```
因此可以把共同框架理解为：
```plain text
                 快慢充共同骨架

充电口
  ↓
充电允许
  ↓
充电建立
  ↓
充电过程
  ↓
充电结束
  │
  ├──── 国标协议 / 接口机制 ────┐
  │                              │
  │  慢充：CC / CP / PWM / S2   │
  │  快充：硬线 + 数字通信协议   │
  │                              │
  └──────── Evidence ────────────┘

同时受到共有边界系统约束：

BMS / Pack
高压安全
HVIL / IMD
HV Bus / 接触器 / 预充
热管理
低压供电
整车状态
```
---
## 2. 快慢充真正的重要分叉
两者并不是两套完全不同的充电逻辑。
共同点是：
> **共享充电生命周期，受到共同车辆边界约束。**
真正的重要分叉是：
> **接口实现不同、通信方式不同、功率执行位置不同。**
```plain text
慢充

EVSE提供AC
↓
车内OBC完成AC→DC
↓
Pack
```
```plain text
快充

桩侧功率模块完成AC→DC
↓
车辆通过协议表达请求 / 能力 / 边界
↓
桩执行DC输出
↓
Pack
```
因此慢充中：
```plain text
Capability
↓
Target
↓
Execution
↓
Actual
```
大量 Evidence 存在于车辆内部，可以通过车辆 Signal、OBC<br>状态及电气测量观察。
而快充中的类似控制链横跨车桩：
```plain text
车辆需求 / 边界
↕
国标通信
↕
桩侧目标 / 功率执行
↕
实际输出
```
所以要完整恢复快充控制过程，更依赖**国标通信报文 + 车桩两侧 Evidence**。
---
# 3. 控制树 — Evidence — 诊断树
## 3.1 状态和变量是共同地基
从电池系统开始引入”状态和变量”，使 Evidence 有了真正的基础。
```plain text
状态
变量
条件
判断
请求
目标
执行
反馈
```
有了这些对象，“系统正常 / 异常”才可以被拆成能够证明或证伪的命题。
例如：
```plain text
Charge Allowed
A₂
IAC_target
IAC_actual
OBC Ready
Contactor State
HV Bus Voltage
Pack Current
SOC
Temperature
```
因此：
> **状态与变量提供诊断语言，Evidence 才有明确的观察对象。**
---
## 3.2 控制树回答 Should / What
控制树是正向的：
```plain text
Condition
↓
Decision
↓
Request / Target
↓
Execution
↓
Feedback
↓
Expected State
```
它回答：
> **What：系统做什么？**
> **Should：为了让功能成立，哪些条件、状态和动作应该依次成立？**
所以控制树的本质是：
> **把正常功能如何成立的控制原理梳理和表达清楚。**
例如慢充核心链：
```plain text
CC
↓
CP
↓
Ready
↓
EVSE输出
↓
AEVSE
↓
A₂
↓
IAC_target
↓
高压路径
↓
OBC功率转换
↓
IAC_actual
↓
Pack
```
它定义的是一个正常世界：
> **如果慢充正确运行，关键 Evidence 应该怎样依次出现。**
---
## 3.3 Evidence 连接模型与现实
控制树定义：
```plain text
Expected Evidence
应该发生什么？
```
真实车辆提供：
```plain text
Observed Evidence
实际上发生了什么？
```
因此：
```plain text
             控制树
               │
       Should / What
               │
               ↓
        Expected Evidence
               │
          ─────┼─────
               │
        Observed Evidence
               │
               ↓
             诊断树
               │
              Why
```
Evidence 可以来自：
```plain text
Signal
ECU状态
DTC / Freeze Frame
通信报文
电压
电流
波形
温度
机械状态
其他独立物理测量
```
必须始终记住：
> **Evidence 本身也可能失效。**
例如 ECU 报告的 `IAC_actual`<br>是控制器看到的实际值；当它与物理现象矛盾时，还需要独立电气测量证明真实世界发生了什么。
---
## 3.4 诊断树回答 Why
诊断树从异常现象反向出发：
```plain text
Abnormal State
↑
Expected State为什么没有成立？
↑
Feedback？
↑
Execution？
↑
Request / Target？
↑
Decision？
↑
Condition？
```
它回答：
> **Why：为什么本来应该成立的功能没有成立？**
诊断过程就是不断寻找：
```plain text
最后一个已经成立的状态
↓
第一个没有成立的 Evidence
↓
对应节点 / 分支
↓
继续验证
↓
故障边界收敛
```
所以诊断树的本质是：
> **从异常结果出发，沿控制关系反向溯源，寻找是哪一个节点、哪一个分支、哪一个叶子故障导致异常。**
---
# 4. 两棵树：同源、反向、不同目的
控制树与诊断树共享：
```plain text
状态
变量
条件
判断
请求
目标
执行
反馈
系统边界
```
因此二者**同源**。
但它们不能合并，因为回答的问题不同。
```plain text
控制树
正常功能怎样成立？
Should / What
↓
正向展开


诊断树
功能为什么没有成立？
Why
↑
反向收敛
```
例如：
```plain text
IAC_target
↓
OBC执行
↓
IAC_actual
```
在控制树中表达：
> OBC 如何把目标转化为实际交流输入电流。
到了诊断树中，同样的对象变成：
```plain text
IAC_target > 0？
↓
执行条件成立？
↓
OBC进入执行状态？
↓
IAC_actual跟随了吗？
```
回答：
> **充电电流为什么没有建立？**
因此：
> **对象相同，角度不同；变量状态共享，任务不同。**

# 5. L3诊断方法链
这轮学习后，可以把方法论进一步收敛为：
```plain text
系统理解
↓
状态 / 变量建模
↓
控制主线
↓
控制树
Should / What
↓
Evidence Requirement
“应该看到什么？”
↓
Signal / 状态 / 通信 / 测量
↓
Observed Evidence
“实际上看到了什么？”
↓
Expected ≠ Observed
↓
诊断树
Why
↓
故障边界收敛
```
进一步落到具体车型：
```plain text
通用系统模型
↓
具体车型
↓
Signal Candidate
↓
Signal Verification
↓
基线采集
↓
真实时间序列
↓
Evidence
↓
车型控制树实例化
↓
真实故障诊断
```
---
# 6. 三者之间最重要的关系
```plain text
控制树
定义正常世界
↓
“这里应该发生什么？”

Evidence
证明现实世界
↓
“这里实际上发生了吗？”

诊断树
解释两者差异
↓
“为什么没有发生？”

最终
↓
故障边界收敛
```
没有 Evidence：
> 控制树容易停留在理论模型。
没有控制树：
> Signal 和测量值容易变成一堆不知道为什么要看的数据。
没有诊断树：
> 即使发现异常 Evidence，也不知道如何继续向故障边界收敛。
三者必须连起来。

## 四句话
> **控制树定义正常世界。**
> **Evidence 证明现实世界。**
> **诊断树解释两者为什么不同。**
> **诊断的终点，是找到第一个无法被 Evidence<br>证明的关键状态，并把故障边界收敛到下一维修层级可以接手的对象。**
---
## 一句话记忆
> **状态与变量提供语言，控制树建立 Should / What，Evidence<br>连接模型与现实，诊断树回答 Why。**
