# Round 4 分析过程记录

本轮严格使用 Workspace 内的采集资产、Round 4 已批准计划与 Round 3 已审计产物，不访问外部答案、网络或其他历史会话。

处理顺序：先检查 session/event/photo/CAN 完整性；再用 ASC 头部墙钟相对 `session.start_clock` 重建脚本时间；按实际 E02–E13 时间构造 S0–S5 预注册窗口；对 Round 3 的 16 个字节组计算完整字节和候选掩码逐轮轨迹；然后拆 bit 分类；最后进行全总线补充盲扫和方向匹配。

用户补充的轮间“重新送风、6 挡降至 2 挡再关闭”只用于说明会话之间的复位背景，不作为会话内标签。用户报告的 4–6 s 声音没有同步音频 Evidence，因此未据此筛选或命名 CAN 观察。

分析中发现两个重要结构性结果：`0x20C B1` 的 Round 3 组内 b4 跟随 HVAC/送风开启，而 b3 只随 A/C 状态变化；`0x282 B0` 的 b2 跟随 HVAC/送风开启，而 b6 对风量 2→6 敏感。因此两个旧字节组明确需要拆分。`0x20C B4.b1` 在本轮为常值，不再保持 Round 3 的状态相关性。

正式结论停止在实验相关 raw observation 层，不赋予 DBC Signal、请求/许可/执行层或 ECU 来源身份。
