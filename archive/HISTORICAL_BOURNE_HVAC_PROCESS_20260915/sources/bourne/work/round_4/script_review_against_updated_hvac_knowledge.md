# Round 4采集脚本知识对照Review

## 1. Review依据与结论

依据更新后的`knowledge_snapshot/座舱舒适系统/空调系统HVAC/空调系统HVAC.md`，HVAC不能只按“开/关”理解。知识文档明确区分：

1. 用户请求与Profile设置；
2. 环境状态与系统计算需求；
3. 整车许可、可用性、功率限制；
4. 执行目标与执行器运行；
5. 空气/冷媒/能量的物理结果；
6. 反馈、保护和故障。

现有Round 4脚本适合验证**设置层变化及其相关CAN观察能否被拆分**，也可以发现不同粗粒度响应层级；但它不能仅凭当前动作给任何raw字段赋予`Cooling_enable`、`Comp_active`、`Ncomp_actual`等具体名称。

本Review结论：脚本方向正确、比Round 3重复OFF/ON的信息增益高，但当前版本只能可靠承担“第一阶段字段解耦”。若目标包含实际制冷链确认，外部Evidence和环境变量记录仍不足；若目标包含字段结构恢复，风量只有2和6两个水平也不足以确认编码规律。

## 2. 采集计划究竟想验证什么

### 2.1 对Round 3的直接验证

Round 3留下23个二态raw bit和16个字节级边界假设。Round 4不再问“它们是否跟随HVAC总开关”，而是问：

- 哪些只要HVAC/通风开启就保持变化；
- 哪些随风量设定变化；
- 哪些只在A/C开启时变化；
- 哪些在A/C关闭后立即回归；
- 哪些有数秒建立或缓慢退出，表现为动态过程而非设置位；
- 同字节多个bit是固定组合、不同子字段还是连续量跨阈值产生的同步位。

### 2.2 可接受的输出名称

本轮最多先得到：

- HVAC/通风开启相关raw字段假设；
- 风量设置/风机链相关raw字段假设；
- A/C设置/制冷链相关raw字段假设；
- 物理或控制动态相关raw字段假设；
- 仍无法分类的raw字段。

这些名称表达实验相关性，不等于知识文档中的标准变量已经被识别。

## 3. 六个状态在知识控制树中的作用

| 转换 | 人为保持与改变 | 主要激励层 | 可能共同变化但不能预设的层 |
|---|---|---|---|
| S0→S1 | HVAC OFF→ON；A/C保持OFF；风量设为2 | `HVAC_request/state`、`Ventilation_request`、`Blower_set` | `HVAC_enable`、`Ventilation_active`、`Blower_request/active`、目标/实际转速、风量、风门动作 |
| S1→S2 | 只把风量2→6 | `Blower_set`、风量请求 | `Nblower_target/actual`、`Airflow_actual`、功率变化、噪声变化 |
| S2→S3 | 风量6不变，只打开A/C | `AC_state`、`Cooling_request`候选激励 | `Cooling_demand/enable/active`、`Comp_request/active`、目标/实际转速、功率、压力、阀门、蒸发器/出风温度 |
| S3→S4 | 只关闭A/C，送风继续 | A/C请求/设置的反向验证 | 压缩机退出、压力均衡、蒸发器和出风温度惯性、后吹逻辑 |
| S4→S5 | HVAC ON→OFF | HVAC与通风关闭请求 | 风机停止、风门停留/归位、许可撤销、执行退出 |

其中S2≈S4是区分“A/C可逆设置字段”的关键对照；如果某字段S2与S4不同，不应立即判为失败，它可能反映热状态、压力状态、蒸发器温度或退出后的控制惯性。

## 4. 与四条主线的对应

### 控制主线

脚本明确操纵HVAC开关、风量和A/C三类人机输入，能够观察“需求/目标/许可/控制/执行/反馈”是否出现分层响应。但是只有输入动作与UI照片时，不能判断每个CAN变化位于控制链哪一层。

### 动力主线

- S1/S2主要激励鼓风机驱动空气流动；
- S3除鼓风机外，可能激励压缩机驱动冷媒循环；
- 当前没有直接记录风机实际转速、空气流量或压缩机实际转速，所以动力执行只能作为候选解释。

### 能量主线

S3理论上增加压缩机电能输入并把座舱热量搬向环境，但脚本没有高压电流/功率、冷媒温压或座舱热量变化的直接测量。出风口温度只能补充局部冷风结果，不能单独证明完整能量链。

### 安全主线

脚本刻意保持正常工况，不激励高压许可不足、功率降额、压力保护、过温或故障。因此Round 4结果不能识别或排除`HVAC_derate`、`Cooling_derate`、保护与故障字段，也不能证明候选跨限制工况仍成立。

## 5. 更新知识暴露出的具体设计缺口

### 5.1 环境温度不等于制冷需求

计划写“环境显示温度≥25°C、设定20°C”，但知识文档表明`Cooling_demand`还可能依赖`Tcabin`、`Solar_load`、湿度、目标状态和控制策略。环境温度高于设定温度并不能证明座舱制冷需求成立。

因此：

- 该条件可以提高出现制冷需求的概率；
- 不能作为`Cooling_demand=1`的事实标签；
- 若没有座舱温度或执行Evidence，只能把S3标为“A/C UI开启状态”，不能标为“制冷运行状态”。

### 5.2 A/C状态不等于压缩机运行

UI中的A/C蓝色最接近`AC_state`或`Cooling_request`外部事实。它与`Cooling_enable`、`Cooling_active`、`Comp_request`、`Comp_active`之间隔着可用性、许可、功率限制和控制决策。S2→S3可以筛出“A/C相关”观察，但不能仅按早晚完成变量命名。

### 5.3 风量设定不等于风机实际转速

风量2→6直接标注的是`Blower_set`。可能随后变化的`Blower_request`、`Nblower_target`、`Nblower_actual`、`Airflow_actual`属于不同层。UI照片只证明设定层；若没有风速、风量或转速测量，不能确认实际层。

### 5.4 出风口温度证据仍有边界

固定探头测得`Toutlet`下降，可以支持冷风输出结果，但仍不能单独识别压缩机转速、压力、膨胀阀开度或制冷能力。S3→S4后温度延迟恢复属于合理热惯性，不能要求与A/C设置位同步二态翻转。

### 5.5 两个风量水平不足以恢复编码

风量2与6能够识别“对风量变化敏感”的字段，但不能区分：

- 二档枚举；
- 原始等级值；
- 比例缩放连续值；
- 目标转速；
- 实际转速或空气流量；
- 仅在跨过某阈值时翻转的bit。

所以当前计划能筛出风量相关字段，却不能完成`Blower_level`或`Nblower_*`的编码恢复。

### 5.6 固定内循环和固定配风只是控制变量

固定设置可以减少混杂，但不能证明`Recirc_actual`或风门实际位置没有变化。系统可能在启动、制冷或保护过程中执行内部策略。未单独激励这些设置时，任何循环/风门字段都不能被识别。

### 5.7 多个CAN ID的来源关系仍无法解决

即使几个ID对六状态呈现相同轨迹，也不能仅凭时序判断谁是请求源、网关复制或消费者派生。被动单总线采集缺少发送节点、网络拓扑或受控拒绝条件，Round 4只能加强“共同响应模式”，不能确认权威来源。

## 6. 当前脚本能回答与不能回答的问题

### 能回答

- Round 3的16个字节组中，哪些只跟随总开关、哪些对风量或A/C状态敏感；
- 完整字节与候选掩码在六状态、五会话中的取值轨迹是否重复；
- S2→S3→S4是否呈可逆模式；
- 哪些观察近事件变化，哪些在数秒后或缓慢变化；
- UI设定、CAN观察与可选出风温度之间是否存在稳定时间关联。

### 不能回答

- 任一字段的最终DBC名称、位宽、比例、单位或发送ECU；
- `Cooling_demand`、`Cooling_enable`和`Cooling_active`之间的确定归属；
- 压缩机目标/实际转速、输入功率、压力、膨胀阀开度等具体变量；
- A/C请求被拒绝、降额、保护或故障时字段如何表现；
- AUTO、除雾、制热、热泵或整车热管理协同；
- 跨环境、SOC、车辆或软件版本的普适性。

## 7. 对现脚本的Review裁决

| 项目 | 裁决 | 理由 |
|---|---|---|
| 相比Round 3的信息增益 | PASS | 从二态OFF/ON扩展为总开关、两档风量、A/C与回归对照 |
| UI设置层解耦 | PASS | S1/S2/S3/S4的单变量操作关系清晰 |
| 可逆性检查 | PASS | S2与S4、S0与S5提供回归对照 |
| 五会话重复性 | PASS | 保持逐轮判定，避免总体多数掩盖失败 |
| 字段结构恢复 | PARTIAL | 仅两个风量水平，只能筛选敏感字段，不能恢复可靠编码 |
| 实际送风确认 | PARTIAL | UI风量不是实际转速/流量；缺少直接测量 |
| 实际制冷确认 | CONDITIONAL | 只有固定出风温度探头时可支持冷风结果；仍不能单独证明完整制冷执行链 |
| 许可/限制/保护识别 | OUT_OF_SCOPE | 脚本仅覆盖正常工况，没有拒绝、降额或故障激励 |
| 具体语义与发送源确认 | NOT_SUPPORTED | 当前Evidence不足，不能命名DBC Signal或权威ECU |

## 8. Review后建议

在开始现场采集前，应先明确本批目标属于哪一层：

- 若目标是**Round 3字段的UI设置层解耦**，现脚本可以执行；结果必须停在“相关raw字段假设”。
- 若目标是**恢复风量字段编码**，现脚本的2/6两点不足，需要增加中间等级或阶梯变化。
- 若目标是**确认实际制冷运行链**，必须补充座舱/出风温度或电功率、压缩机运行等独立Evidence；A/C蓝色不能替代。

因此，本脚本不是“一次确认整个HVAC控制树”的方案，而是一个分层验证入口。它最可靠的任务是拆开`HVAC_state/Blower_set/AC_state`相关观察，并为后续是否存在执行与物理结果层候选提供线索。
