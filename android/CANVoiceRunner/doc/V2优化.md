# V2 优化

## 本轮优化目标

针对现有采集播报 App 在实际使用中发现的问题，进行一次范围明确、逐步推进、可验证的版本优化，使 App 更好地支持实验现场执行与真实事件记录，并为后续数据分析提供可靠的现场信息。

本轮工作由用户与 Codex 按实际需要逐项讨论、确认和完成；未经共同确认，不提前扩展具体需求、设计方案或实现范围。

## 任务名称

1. 工作交流与协作方式规范
2. 后台计时与语音播报优化
3. 计划时间与实测事件时间分离
4. 事件照片记录优化
5. 事件与照片备注支持
6. 事件时间线结构化导出
7. 数据可靠性与持久化优化
8. 向后兼容与版本验收

### 开始时间

### 结束时间

### 当前状态

### 内容审核状态

### 设计文档

[计划时间与实测事件时间分离设计.md](V2优化/计划时间与实测事件时间分离设计.md)

### 目标

保留采集脚本中的计划时间（`planned_time`）作为现场操作提示，同时由用户在真实动作发生后通过最简单的现场操作记录实测事件时间（`observed_time`），供后续 ASC 分析建立可靠的事件时间锚点。

### 要求

1. 系统必须明确区分真实采集时钟（`session_elapsed_time`）和脚本执行时钟（`script_elapsed_time`）。
2. 真实采集时钟从开始采集持续到正常结束或强行中止，永不暂停、冻结、回拨或重新计时；前后台切换和脚本暂停均不得打断它。
3. 脚本执行时钟用于推进计划操作和语音提示，允许暂停和恢复；暂停期间不推进脚本时间，恢复后从原脚本位置继续。
4. 每个事件至少区分 `planned_time`、`observed_time`、`action` 和 `status`。
5. `planned_time` 属于脚本执行时间轴，保留原始剧本值；`observed_time` 必须取自连续流淌的真实采集时间轴。
6. 事件允许提前完成、按计划完成、推迟完成或明确跳过；脚本是执行指导，不得反向覆盖真实实验记录。
7. `observed_time` 只在获得真实操作记录时写入；未经确认的事件保持 `observed_time = null`，不得用 `planned_time`、播报时间或脚本时间自动填充。
8. 事件状态至少包含 `pending / completed / skipped`。`pending` 不构成强制现场待办，也不得阻塞后续采集。
9. 用户明确跳过事件时记录 `skipped`；跳过时刻取自真实采集时间轴，但不得伪造该事件的 `observed_time`。
10. 暂停是会话的脚本执行状态，不是事件状态，也不暂停真实采集时钟。
11. 前后台切换后，当前服务进程仍存活时，两条时钟、暂停状态、事件状态和已记录的实测时间不得丢失。
12. 保持现有采集脚本格式兼容，不修改 Raw ASC，不提前实现照片、备注、多 Session 或最终结构化 Timeline 导出。

### 原始验收脚本

原始材料未提供任务 3 专用的完整现场脚本。任务书提供的示例事件为：

```text
Event E03
Planned Time: 00:30
Action: 插入充电枪
```

示例验收语义：App 在 `00:30.000` 播报操作提示；用户于 `00:34.827` 点击“完成 / 记录事件”后，必须分别保存：

```text
planned_time  = 00:30.000
observed_time = 00:34.827
status        = completed
```

若用户未确认，则 `observed_time = null`；若用户点击“跳过”，则 `status = skipped` 且 `observed_time = null`。
