### 目标

保留采集脚本中的原始 `plan_time` 作为播报计划；用连续流淌的 `script_time` 记录计划节点实际触发的时间。正常事件在播报触发后自动记为 `triggered`，仅在现场明确未执行时由用户标记为 `skipped`，避免逐项人工确认。

### 要求

1. Clock 只记录现实钟表时间，字段为 `start_clock` 和 `end_clock`；开始采集时记录前者，正常结束或 `abort` 时记录后者。
2. Clock 的界面显示可采用时分秒，底层记录必须包含日期、时区和真实可用的毫秒精度；不得伪造设备并不具备的微秒级绝对时钟精度。
3. `plan_time` 是脚本文件中每个事件的原始计划时间，用于播报调度和记录参考，永远保持脚本原值。
4. 暂停会话时允许暂停计划播报进度；恢复后继续调度，但不得修改事件的原始 `plan_time` 或脚本时间窗口总时长。
5. `script_time` 是从开始采集的零点起真实连续流淌的实验时间，直到正常结束或 `abort`；暂停、前后台切换和现场操作均不得使其停止、冻结、回拨或重新计时。
6. `script_time` 底层使用单调时钟，以整数微秒 `script_time_us` 记录，避免浮点误差；显示精度可低于记录精度。
7. 每个采集 Event 初始为 `pending`；计划节点实际触发播报后自动变为 `triggered`，并记录当时的 `trigger_script_time_us`，不要求用户逐项确认。
8. “跳过”只作用于已经触发并成为当前 Event 的事件。现场明确未执行该事件时，用户将其标记为 `skipped` 并记录 `skip_script_time_us`；原始 `trigger_script_time_us` 必须保留。不允许跳过尚未触发的下一个 Event，不存在 `pending → skipped`。
9. 事件状态使用 `pending / triggered / skipped`。`triggered` 表示计划节点已触发并默认按剧本执行，不声称 App 已独立确认物理动作完成。
10. 暂停是会话/播报调度状态，不是事件时间，也不暂停 `script_time`。
11. `script_time` 与 ASC 必须共享时间原点，或存在确定、可审计的时间映射；不得仅凭 App 内部单调时间假定已经与 ASC 对齐。
12. `action` 始终表示脚本定义的实验目标动作；UI 的“跳过”等操作只能改变执行记录，不得覆盖或改写实验事件语义。
13. 前后台切换后，当前服务进程仍存活时，Clock 锚点、`script_time`、暂停状态、事件状态和已记录时间不得丢失。
14. 保持现有采集脚本格式兼容，不修改 Raw ASC，不提前实现照片、备注、多 Session 或最终结构化 Timeline 导出。

### 原始验收脚本

原始材料未提供任务 3 专用的完整现场脚本。任务书提供的示例事件为：

```text
Event E03
Planned Time: 00:30
Action: 插入充电枪
```

示例验收语义：原始 `plan_time` 为 `00:30.000`。若会话发生暂停，App 在连续 `script_time` 的 `00:34.827` 实际触发播报，则必须分别保存：

```text

trigger_script_time   = 00:34.827
status                = triggered
```

正常情况无需用户确认。若现场明确未执行该动作，用户标记“跳过”，则 `status = skipped` 并记录 `skip_script_time_us`；不得删除已经存在的触发时间。

### 目标

### 要求

1. 录音以整个 Session 为作用域，不绑定某一个 Event，也不与照片或备注建立外键、关联表或自动语义关系；这些证据只分别保留各自时间。

3. 录音不得阻塞拍照、备注、跳过、暂停播报或结束采集等现场操作。
4. 每个录音文件至少记录录音请求、实际开始与实际结束的 Clock；请求和实际开始发生在 Session 零点前后时，使用有符号 `recording_request_offset_us`、`recording_start_offset_us` 表达相对零点的位置，结束使用 `recording_end_script_time_us`；同时记录文件名、文件 URI、音频格式、采样率、声道数和结束原因。
5. 录音内容以手机麦克风采集的车内声音为准；TTS 若被麦克风从扬声器环境声中录入可以保留，但不把“系统内部音频直录”作为默认目标。
6. 使用适合长时间语音记录的压缩格式，优先考虑单声道 AAC/M4A，避免未压缩 PCM/WAV 造成过大文件。
7. 麦克风权限被拒绝、录音启动失败、存储不足或录音被系统中断时，不得阻止主要采集 Session 继续；必须明确显示未录音或录音失败状态并记录失败原因。
8. 采集结束或 `abort` 时必须停止并封装当前录音文件；已成功保存的文件允许保留。
9. App 进入后台或锁屏后应尽可能继续录音，并与现有前台服务共同工作；目标手机上的实际限制必须通过真机测试确认。
10. 当前阶段不设计语音转文字、自动摘要、降噪处理、音频剪辑或多轨录音。
11. 录音是采集前选项，默认关闭。只有用户在开始采集前明确打开，本次 Session 才录音。
12. 录音选项一旦进入准备倒计时即锁定，采集中不提供开始、停止或重新开始录音操作。
13. 已启用录音时，App 在准备倒计时阶段自动启动录音，在正常结束或 `abort` 时自动停止，目标是形成完整覆盖 Session 的单个录音文件。
14. 每次新 Session 的录音选项恢复为默认关闭，不沿用上一次启用状态，避免用户无意录音。
15. 已启用录音时，在准备倒计时阶段完成权限状态检查、录音器初始化并提前启动录音，再建立 Session 的 `script_time = 0`，尽量保证 Session 开头不丢失声音。
16. 使用有符号整数微秒 `recording_start_offset_us` 记录首个有效音频时间点相对 Session 零点的偏移：负值表示录音提前开始，正值表示录音延后开始，零表示两者重合；不得把录音文件起点直接假定为 Session 零点。
17. `recording_start_offset_us` 必须注明测量方法与有效精度；无法取得首个有效音频时间戳时，不得把 API 调用耗时伪装成精确音频偏移。

20. 录音起点优先使用 `AudioRecord.getTimestamp(..., TIMEBASE_BOOTTIME)` 返回的 `AudioTimestamp`，根据 `framePosition`、`nanoTime` 和采样率反推首个有效音频帧的捕获时间，再映射到与 `SystemClock.elapsedRealtimeNanos()` 同源的 Session 零点。
21. `recording_start_offset_us` 使用整数微秒存储，但工程准确度目标为正负 20 毫秒；该精度已经确认足以服务当前 CAN 数据采集，不宣称微秒级实际准确度。
22. 若整段录音无法取得可靠 `AudioTimestamp`，录音文件允许保留，但 `recording_start_offset_us = null`，并记录 `recording_start_method = TIMESTAMP_UNAVAILABLE`，不得用 API 调用时间冒充音频首帧时间。
23. 录音文件名以本次采集脚本的原始文件名为主体，去除脚本扩展名后附加“录音”和录音起始 Clock 时间戳，例如脚本 `TM3-016_语音执行脚本.txt` 对应 `TM3-016_语音执行脚本_录音_20260909_153022_615.m4a`。同一脚本多次采集不得覆盖既有录音；原始脚本文件名必须另存为元数据，文件名安全清洗不得改写该原始值。

### 目标

将 Session、Event、照片、备注和录音统一保存为稳定、机器可读的 JSON；同时保留原 CSV Event Timeline，作为 Android 根据实际采集时间计算形成的事件结果，供 Python 分析程序把采集脚本、事件时间点与原始 ASC 对齐。任务 7 没有新增界面设计。

### 设计原则

1. JSON 是完整 Session 与附属证据的数据文件；CSV 是面向 Python/ASC 分析的精简事件时间线。两者职责不同，必须同时保留，不视为内容重复。
2. JSON 顶层分别保存 `session`、`events`、`photos`、`notes` 和 `audio_recording`，保持各类对象边界清楚；`audio_recording` 只保存录音文件索引和录音自身元数据，不包含音频数据。
3. JSON 必须完整保存 Session Clock、Event 原始动作、`plan_time`、状态、触发时间和跳过时间。
4. 照片和备注继续保留各自已经审核的目标标识；录音只属于 Session，不与 Event、照片或备注建立关系。
5. 不通过数组顺序表达唯一时间关系；消费者按明确 ID、顺序字段和时间字段解释。
6. 逻辑删除的备注仍导出，并明确 `deleted = true`，不得静默丢弃审计记录。
7. JSON 中的时间数量统一使用整数，空值使用 `null`，状态使用已审核的英文枚举，不输出含糊的展示文字代替数据。
8. 不修改 Raw ASC，不在 App 中解析 CAN、切割 ASC 或生成诊断结论。

### CSV Event Timeline

Session 目录必须保留 `event_timeline.csv`。CSV 只记录采集脚本 Event 及其时间计算结果，供 Python 将采集脚本、Android 现场事件与原始 ASC 对齐；照片、备注、录音和其他 Session 附属信息继续保存在 `session.json`。

CSV 沿用既有时间线思路，但不再使用 `session_start`、`session_end` 特殊记录行。采集脚本中的“开始采集”和“结束采集”本身就是普通 Event。字段固定如下：

| 字段 | 含义 |
|---|---|
| `event_id` | Event 可读编号 |
| `action` | 采集脚本中的原始动作 |
| `plan_time_s` | 脚本原始计划秒数，永不重算或覆盖 |
| `status` | `pending / triggered / skipped` |
| `session_script_time_us` | Event 的 3—2—1 倒计时结束后“滴”声发生时，相对 Session `script_time = 0` 的真实偏移微秒数 |
| `skip_script_time_us` | Event 触发后，用户确认该动作未执行并点击“跳过”的真实偏移微秒数；未跳过为空 |
| `clock_iso` | 根据 Session Clock 锚点和 `session_script_time_us` 重算的 Event 绝对 Clock，可读格式包含日期、毫秒和时区 |
| `clock_epoch_ms` | 与 `clock_iso` 对应的 Unix Epoch 毫秒，供 Python 直接计算 |

JSON 中的 `trigger_script_time_us` 与 CSV 中的 `session_script_time_us` 表达同一个 Event 滴声时间。CSV 使用后者作为面向分析程序的字段名，避免同时输出两个含义重复的列。

时间重算关系为：

```text
event clock ≈ session.start_clock + session_script_time_us
```

其中相对 Event 时间继续保留整数微秒；绝对 Clock 受设备墙上时钟精度限制，以毫秒保存和输出。Python 分析程序应保留相对微秒字段，不得仅从格式化的 `clock_iso` 反推事件间隔。

示例：

| event_id | action | plan_time_s | status | session_script_time_us | skip_script_time_us | clock_iso | clock_epoch_ms |
|---|---|---:|---|---:|---:|---|---:|
| E01 | 开始采集 | 0 | triggered | 125000 |  | 2026-09-10T09:30:00.125+08:00 | 1789003800125 |
| E02 | 手动下降，按住 | 20 | triggered | 21427836 |  | 2026-09-10T09:30:21.428+08:00 | 1789003821428 |
| E03 | 松开 | 22 | skipped | 23550642 | 24100821 | 2026-09-10T09:30:23.551+08:00 | 1789003823551 |
| E04 | 手动上升，按住 | 37 | triggered | 39102318 |  | 2026-09-10T09:30:39.102+08:00 | 1789003839102 |
| E05 | 结束采集 | 60 | triggered | 62500317 |  | 2026-09-10T09:31:02.500+08:00 | 1789003862500 |

“跳过”只允许作用于已经触发的当前 Event。因此不存在未触发即为 `skipped` 的行；所有 `skipped` 行都必须同时具有 `session_script_time_us` 和 `skip_script_time_us`。状态为 `skipped` 表示滴声已经发生，但对应实验动作未实际执行，Python 不得把该行当作有效动作发生点。
