# V2 优化

## 本轮优化目标

针对现有采集播报 App 在实际使用中发现的问题，进行一次范围明确、逐步推进、可验证的版本优化，使 App 更好地支持实验现场执行与真实事件记录，并为后续数据分析提供可靠的现场信息。

本轮工作由用户与 Codex 按实际需要逐项讨论、确认和完成；未经共同确认，不提前扩展具体需求、设计方案或实现范围。

### 目标

保留采集脚本中的原始 `plan_time` 作为播报计划；用连续流淌的 `script_time` 记录计划节点实际触发的时间。正常事件在播报触发后自动记为 `triggered`，仅在现场明确未执行时由用户标记为 `skipped`，避免逐项人工确认。

### 要求

1. Clock 只记录现实钟表时间，字段为 `start_clock` 和 `end_clock`；开始采集时记录前者，正常结束或 `abort` 时记录后者。
2. Clock 的界面显示可采用时分秒，底层记录必须包含日期、时区和真实可用的毫秒精度；不得伪造设备并不具备的微秒级绝对时钟精度。
3. `plan_time` 是脚本文件中每个事件的原始计划时间，用于播报调度和记录参考，永远保持脚本原值。
4. 暂停会话时允许暂停计划播报进度；恢复后继续调度，但不得修改事件的原始 `plan_time` 或脚本时间窗口总时长。
5. `script_time` 是从开始采集的零点起真实连续流淌的实验时间，直到正常结束或 `abort`；暂停、前后台切换和现场操作均不得使其停止、冻结、回拨或重新计时。
6. `script_time` 底层使用单调时钟，以整数微秒 `script_time_us` 记录，避免浮点误差；显示精度可低于记录精度。
7. 每个采集 Event 初始为 `pending`；计划节点实际触发播报后自动变为 `triggered`，并记录当时的 `trigger_script_time_us`，不要求用户逐项确认。
8. 现场明确未执行某事件时，用户将其标记为 `skipped` 并记录 `skip_script_time_us`；如果事件已经触发，原始触发记录仍须保留。
9. 事件状态使用 `pending / triggered / skipped`。`triggered` 表示计划节点已触发并默认按剧本执行，不声称 App 已独立确认物理动作完成。
10. 暂停是会话/播报调度状态，不是事件时间，也不暂停 `script_time`。
11. `script_time` 与 ASC 必须共享时间原点，或存在确定、可审计的时间映射；不得仅凭 App 内部单调时间假定已经与 ASC 对齐。
12. `action` 始终表示脚本定义的实验目标动作；UI 的“跳过”等操作只能改变执行记录，不得覆盖或改写实验事件语义。
13. 前后台切换后，当前服务进程仍存活时，Clock 锚点、`script_time`、暂停状态、事件状态和已记录时间不得丢失。
14. 保持现有采集脚本格式兼容，不修改 Raw ASC，不提前实现照片、备注、多 Session 或最终结构化 Timeline 导出。

### 原始验收脚本

原始材料未提供任务 3 专用的完整现场脚本。任务书提供的示例事件为：

```text
Event E03
Planned Time: 00:30
Action: 插入充电枪
```

示例验收语义：原始 `plan_time` 为 `00:30.000`。若会话发生暂停，App 在连续 `script_time` 的 `00:34.827` 实际触发播报，则必须分别保存：

```text
plan_time             = 00:30.000
trigger_script_time   = 00:34.827
status                = triggered
```

正常情况无需用户确认。若现场明确未执行该动作，用户标记“跳过”，则 `status = skipped` 并记录 `skip_script_time_us`；不得删除已经存在的触发时间。
