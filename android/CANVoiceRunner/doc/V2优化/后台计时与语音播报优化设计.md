# 后台计时与语音播报优化设计

## 审核状态

已审核通过。

## 问题现象

当前 App 在前台运行时可以按照采集脚本计时和播报。实际采集过程中切换到 CAN 采集软件、相机或其他 App 后，计时和语音播报可能受到影响；返回 App 时，当前采集状态也缺少可靠的恢复来源。

如果系统调度暂停后一次越过多个计划事件点，当前实现还可能永久漏掉已经过去的播报节点。

## 问题原因

当前计时、脚本调度、语音播报和运行状态全部由主界面（`MainActivity`）管理，其生命周期依赖界面。App 进入后台、界面被重建或进程受到系统限制时，这些能力无法获得可靠保障。

现有步骤查找逻辑只寻找尚未到达的事件点。调度恢复时，已经越过的节点可能无法被正确识别，导致后续状态与真实采集时间轴不一致。

保持屏幕常亮只能作用于前台界面，不能替代 Android 后台运行机制。

## 优化方案

### 1. 运行职责与界面分离

将采集计时、步骤调度和语音播报交给用户主动启动的前台服务（Foreground Service）管理。主界面只负责启动、结束和显示当前状态。

切换到其他 App 后，前台服务继续维护采集时间轴和语音播报；返回 App 后，界面从服务读取当前状态，不重新开始计时。

### 2. 遵循真实采集时间

采集开始后，时间持续真实流逝，不因 App 切换后台、锁屏或系统短暂延迟而暂停或平移脚本时间轴。

播报严格遵循脚本规定的计划事件点：

- 尚未到达的事件点按计划播报；
- 调度恢复时已经过去的事件点直接跳过，不补播；
- 跳过播报不代表对应事件已经执行或完成；
- App 根据真实经过时间显示当前计时和下一个尚未到达的事件点。

### 3. 后台常驻与系统设置

采集期间显示前台服务所要求的常驻通知。App 声明后台运行所需的前台服务权限和服务类型。

第一次使用时提供“后台常驻设置”引导，提示用户允许通知、后台运行，并在 ColorOS 中按需将电池使用设为不受限制。系统允许时跳转到相关设置页面；无法准确跳转时，由用户进入 App 管理手工设置。

Android 没有统一的“后台常驻权限”。App 只能声明平台提供的相关权限并提示用户完成 ColorOS 设置，不得把尚未授予的能力显示为已经生效。

### 4. 设计边界

本任务只优化后台计时、脚本事件点播报和返回前台后的运行状态显示，不增加暂停采集、事件实测时间、照片、备注、ASC 分析或其他后续任务功能。

方案保持现有 Java App 的简洁结构，不引入大型第三方库或复杂架构。

## 测试方法

### 1. 调度逻辑测试

- 验证计划事件点只触发一次播报；
- 验证计时不会因重复刷新产生累计误差；
- 验证短暂调度延迟后，尚未到达的事件点仍按原时间轴执行；
- 验证一次越过多个事件点时，已过去节点不补播，后续节点仍按计划播报；
- 验证结束采集后不再产生播报。

### 2. 前后台测试

使用以下测试脚本：

```text
00:10 播报 A
00:20 播报 B
00:30 播报 C
```

启动后立即切换到其他 App，确认 A、B、C 均在对应计划事件点正常播报；返回 App 后，计时没有重新开始，当前状态和下一个事件点正确。

### 3. 一加 Ace 5 真机测试

在一加 Ace 5 和当前 ColorOS 环境中验证：

- 正常切换其他 App；
- 熄屏和锁屏；
- 解锁后返回 App；
- ColorOS 电池优化开启与设为不受限制；
- 通知权限允许与拒绝；
- 从最近任务界面移除 App。

每个场景记录是否漏播或重复播报、实际播报误差、返回前台后的状态以及常驻通知状态。无法由 App 保证的 ColorOS 行为应明确记录为平台边界。

## 设计结论

任务 2 采用“前台服务维持真实采集时间轴，主界面负责操作和显示”的方案。已经过去的脚本事件点不补播，后续事件点继续依据原计划时间执行；首次使用时引导用户完成 ColorOS 后台运行相关设置。
