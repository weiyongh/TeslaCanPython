# 计划时间与实测事件时间分离设计

## 审核状态

已审核通过。任务 3 的 UI 采用任务 3、4、5 共用的统一主界面布局，见 `采集现场统一UI交互设计.md`。

## 问题现象

当前 App 在计划节点到达时导出 `planned_s,actual_s,event`。其中 `actual_s` 是调度器处理播报的时间，不是事件真实发生的时间，且字段没有明确区分脚本计划、真实实验流逝和现实钟表时间。

现场实验还可能暂停播报流程或跳过动作。正常情况下实验按预先设计的脚本执行，因此计划节点实际触发播报后默认记为已触发采集；只有异常未执行时才要求用户标记跳过。

## 已确认的时间模型

### 1. Clock

Clock 只表示现实世界的钟表时间，只在会话级记录：

```text
start_clock
end_clock
```

- `start_clock`：正式开始采集时记录。
- `end_clock`：正常结束采集或强行中止（`abort`）时记录。
- UI 可以只显示当前 `HH:mm:ss`。
- 底层记录必须包含完整日期、时区和真实可用的毫秒精度，例如 ISO 8601 与 `epoch_ms`。
- Android 绝对时钟如果只能可靠提供毫秒，不得通过补零伪造微秒精度。

Clock 用于表达采集的现实起止时刻，也可以参与建立 App 与 ASC 的时间映射，但不能仅凭格式相同就假定两者已经对齐。

### 2. plan_time

`plan_time` 是原始脚本文件中定义的事件计划时间：

```text
20s  手动下降，按住
```

这里的 `20s` 就是该 Event 的 `plan_time`。

- `plan_time` 用于计划播报和记录参考。
- App 运行时可以读取它进行调度，但不创建一份可被现场操作修改的计划值。
- 暂停、提前完成、延后完成或跳过都不得改写 `plan_time`。
- 暂停只改变播报调度何时继续，不改变原始脚本时间窗口及其总时长。

### 3. script_time

`script_time` 是从正式开始采集的零点起，真实、连续流淌的实验时间：

```text
开始采集：script_time_us = 0
事件发生：script_time_us = 84_827_000
结束采集：script_time_us = 1_352_406_000
```

- 从零开始，持续到正常结束或 `abort`。
- 永远不因 `pause`、前后台切换、锁屏或现场操作而停止、冻结、回拨或重新计时。
- 底层以单调时钟为基础，使用整数微秒 `script_time_us` 保存，避免浮点误差。
- 每个 Event 的真实发生记录都落在 `script_time` 上。

Android 实现可使用 `SystemClock.elapsedRealtimeNanos()` 建立连续时间，换算为整数微秒保存。纳秒 API 提供计数分辨率，不等于设备具备纳秒级现实时间准确度。

## 暂停语义

`pause` 暂停的是计划播报与剧本推进，不是 `script_time`：

```text
运行：script_time 持续；计划播报推进
暂停：script_time 持续；计划播报停止
恢复：script_time 持续；计划播报从暂停位置继续
```

为了实现暂停后的播报续接，程序内部可以维护累计暂停时长或调度偏移，但这只是调度实现数据，不形成另一条对外实验时间，也不得覆盖 `plan_time` 或 `script_time`。

计划节点映射到真实流淌时间时，可以理解为：

```text
实际播报对应的 script_time
    = plan_time
    + 此前累计的会话暂停时长
```

原始 `plan_time` 仍保持不变。

## Event 数据语义

每个事件至少包含：

```text
event_id
action
status
trigger_script_time_us = null
skip_script_time_us = null
```

- `action` 始终是脚本定义的实验目标动作，载入后不得被 UI 操作覆盖。
- `pending`：计划节点尚未实际触发。
- `triggered`：计划节点已经触发播报，默认实验按预先设计的剧本执行；同时记录触发时连续流淌的 `trigger_script_time_us`。
- `skipped`：现场明确未执行该操作；记录用户标记跳过时的 `skip_script_time_us`。

默认状态转换为：

```text
pending ──计划节点实际触发──> triggered
pending ──提前明确跳过─────> skipped
triggered ──事后纠正未执行─> skipped
```

`triggered` 不等于 App 已通过独立证据确认物理动作完成。它准确表达“计划节点已触发，并按实验默认规则视为依剧本采集”，避免使用语义过强的 `completed`。

若已经存在 `trigger_script_time_us`，随后状态被人工纠正为 `skipped`，必须同时保留触发时间和跳过时间。这样可以审计“已经播报，但现场未执行”的偏差过程。

UI 正常情况下不提供逐项“完成”操作。用户只在异常未执行时使用“跳过”，该操作不得改变 `action` 或 `plan_time`。

## 与 ASC 的关系

`script_time` 要用于 ASC 分析，必须满足以下条件之一：

```text
App script_time 与 ASC 共享明确的时间原点
或
存在确定、可复现、可审计的 App script_time ↔ ASC time 映射
```

`start_clock` 和 `end_clock` 是重要的会话锚点，但如果 ASC 没有使用同一绝对时钟，仅记录 Clock 仍不足以自动证明两者对齐。正式导出必须保留时间域和映射依据。

## 当前实现边界

1. `CollectionRunnerService` 已使用单调时钟维护运行时间，可作为 `script_time` 的实现基础。
2. `SessionTimelineRunner` 当前直接按单一经过时间调度，需要增加暂停偏移，但不能停止真实 `script_time`。
3. 当前没有独立 Event 数据对象，需要新增轻量运行期记录，并把计划节点触发与人工跳过分别保存。
4. 当前 `actual_s` 字段必须废止或明确迁移，不能继续冒充事件真实时间。
5. Activity 重建和正常前后台切换可依赖前台服务保留状态；进程终止后的持久化恢复仍属于任务 7。
6. 本任务不实现照片、备注、多 Session、Raw ASC 操作或任务 6 的正式 Timeline Schema。

## 测试要求

1. 开始采集时 `script_time_us = 0`，并记录 `start_clock`。
2. 正常结束或 `abort` 时记录 `end_clock` 和最终 `script_time_us`。
3. `pause` 期间 `script_time_us` 持续增长，计划播报停止。
4. 恢复后计划播报从暂停位置继续，所有原始 `plan_time` 不变。
5. 多次暂停后，调度偏移准确累计且不污染 `script_time_us`。
6. 计划节点实际触发后自动变为 `triggered` 并记录 `trigger_script_time_us`，无需人工确认。
7. 触发前明确跳过时，状态直接变为 `skipped`，并记录 `skip_script_time_us`。
8. 触发后纠正为跳过时，同时保留 `trigger_script_time_us` 和 `skip_script_time_us`。
9. 前后台切换不重置 `start_clock`、`script_time_us`、暂停偏移或事件状态。
10. 所有时间字段可明确识别所属时间域，且不存在 `plan_time` 冒充实际触发时间的情况。
11. 既有任务 2 的后台计时与语音播报测试继续通过。
