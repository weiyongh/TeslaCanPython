# 计划时间与实测事件时间分离设计

## 审核状态

双时钟原则已确认；完整设计待审核。

## 已确认的第一原则

从开始采集到正常结束或强行中止，始终存在一条连续流淌的真实物理时间。App 必须原样记录这段真实时间，不允许任何计时器、脚本暂停、前后台切换或现场操作将其停止、冻结、回拨或重置。

实测事件时间（`observed_time`）必须记录在这条真实采集时间轴上。

## 问题现象

当前 App 在脚本节点到达计划时间时，将一行 `planned_s,actual_s,event` 写入内存列表。其中 `actual_s` 是调度器调用 `onFireStep` 的时间，代表计划播报被处理的时间，不代表用户实际完成车辆操作的时间。

当前实现还只有一个运行计时概念，无法同时表达“真实采集时间持续流淌”和“脚本执行可以暂停、恢复或偏离原计划”。

## 问题原因

当前数据结构只有脚本步骤（`ScriptStep`）和计划调度状态，没有独立的事件记录对象，也没有分离真实采集时钟与脚本执行时钟。计划播报、脚本进度和导出记录被合并在 `CollectionRunnerService.onFireStep` 中。

如果继续使用单一计时值，就无法准确表达以下现场事实：

- 因手忙脚乱而暂停剧本，但真实采集仍在继续；
- 因网络或外部条件而推迟某个操作；
- 提前完成某个操作；
- 明确跳过不合理或无法执行的操作；
- 未进行人工记录，但后续可能从 CAN 中获得 `CAN Observed Time`。

## 现状审计

1. **当前 App 架构**：`MainActivity` 负责操作和显示；`CollectionRunnerService` 负责前台服务、计时、播报和运行期状态；`SessionTimelineRunner` 负责计划节点调度。
2. **现有计时**：使用 `SystemClock.elapsedRealtime()` 计算从 `sessionStartMs` 开始的经过时间，具备建立连续真实采集时钟的基础。
3. **现有调度**：`SessionTimelineRunner` 直接使用上述经过时间推进脚本，尚不支持独立的脚本时钟和暂停。
4. **事件数据模型**：不存在独立 Event 模型。`ScriptStep` 只有 `second`、`title`、`detail`。
5. **Session 数据模型**：不存在独立 Session 对象；服务字段共同表示单次运行会话。
6. **Export 实现**：采集结束后导出内存 CSV；当前 `actual_s` 不是 `observed_time`，字段名称存在语义风险。
7. **Persistence 实现**：没有持久化层。Activity 重建和正常前后台切换依靠仍在运行的服务保留状态；进程被杀后不能恢复。完整持久化属于任务 7。
8. **旧脚本兼容性**：现有 `Ns  动作` 格式可以原样解析，脚本中的秒数可继续解释为原始 `planned_time`。

## 双时钟模型

### 1. 真实采集时钟

真实采集时钟（`session_elapsed_time`）定义为：

```text
session_elapsed_time = SystemClock.elapsedRealtime() - session_start_realtime
```

它从正式开始采集时归零，此后持续增长，直到会话进入 `completed` 或 `aborted`。脚本暂停时也必须继续增长。

以下事实都必须使用这条时间轴记录：

```text
pause_time
resume_time
observed_time
skip_time
session_end_time
abort_time
```

### 2. 脚本执行时钟

脚本执行时钟（`script_elapsed_time`）只负责推进剧本和触发语音提示：

```text
running 时：script_elapsed_time 随真实时间增长
paused  时：script_elapsed_time 保持不变
resume  后：从暂停位置继续增长
```

实现上可以从真实采集时间扣除累计暂停时长，但不得修改或覆盖真实采集时钟：

```text
script_elapsed_time
    = session_elapsed_time
    - accumulated_pause_duration
    - current_pause_duration
```

脚本文件中的 `planned_time` 属于脚本执行时间轴，并保持原始值不变。暂停只改变某个计划节点最终对应的真实提示时刻，不改变剧本中保存的 `planned_time`。

### 3. 实测事件时间

实测事件时间（`observed_time`）必须来自真实采集时钟：

```text
observed_time = current session_elapsed_time
```

它绝不能取自 `script_elapsed_time`。否则脚本暂停后记录的时间会缺少真实经过时长，无法与 ASC 或其他现场证据对齐。

后续分析可能从 CAN 中提取 `can_observed_time`；它同样对应真实采集时间域，但必须和人工/现场记录的 `observed_time` 分列保存，不得互相冒充。

## 会话状态

建议的会话状态（Session State）为：

```text
preparing → running ⇄ paused → completed
                           └──→ aborted
```

- `running`：真实采集时钟和脚本执行时钟都推进。
- `paused`：真实采集时钟继续推进，脚本执行时钟停止。
- `completed`：用户正常结束本次采集。
- `aborted`：用户强行中止或系统无法继续本次采集。

每次 `pause` 和 `resume` 都应作为会话事件记录其真实采集时间，以便复原脚本时钟如何映射到真实时间。

## 事件状态与现场偏差

事件状态（Event Status）至少包含：

```text
pending
completed
skipped
```

- `pending`：尚未获得该事件的真实完成记录；不代表动作一定未发生，也不要求驾驶员立即操作手机。
- `completed`：已经获得真实操作记录，并保存连续真实采集时间域中的 `observed_time`。
- `skipped`：现场明确决定不执行该事件；保存真实采集时间域中的 `skip_time`，`observed_time` 保持为空。

事件允许出现以下实际关系：

```text
observed_time < 计划节点对应的真实提示时间   提前完成
observed_time ≈ 计划节点对应的真实提示时间   接近计划完成
observed_time > 计划节点对应的真实提示时间   推迟完成
observed_time = null                          未记录或跳过
```

提前、接近计划或推迟是根据两条时间轴映射后的派生关系，不应成为覆盖原始时间的手工状态。

## 暂停、推迟与跳过

三者必须区分：

- **暂停（pause）**：暂停整个脚本执行时钟，后续计划操作整体延后；真实采集时钟继续。
- **推迟（defer）**：某个事件暂未完成，但脚本是否继续由现场决定；事件保持 `pending`，直到完成或跳过。
- **跳过（skip）**：明确不执行某个事件，状态变为 `skipped`。

脚本暂停期间，未来计划节点不会被判定为错过，因为脚本时钟没有越过它们。已经到达但尚未完成的事件可以继续保持 `pending`。

## 现场交互原则

1. 单人路测期间不要求驾驶员逐项触屏确认，`pending` 不构成阻塞性的待办。
2. 静态实验或安全条件允许时，可以一键记录当前选定事件，`observed_time` 取点击瞬间的真实采集时间。
3. 无法人工记录时保持 `observed_time = null`；后续可以独立填写 `can_observed_time`，但 App 不自动伪造人工时间。
4. 事件可以在计划提示前完成，因此设计上不能把“到达计划时间”作为允许完成事件的前置条件。
5. 多个事件偏离计划时，不能强迫用户按原顺序逐项清空；具体的安全选择方式仍需在 UI 设计中进一步收敛。

## 建议数据模型

会话至少需要维护：

```text
session_start_realtime
session_elapsed_time
script_elapsed_time
session_status
pause_intervals[]
```

每个事件至少需要维护：

```text
event_id
planned_time
action
status
observed_time = null
skip_time = null
```

`planned_time` 属于脚本时间域；`observed_time` 和 `skip_time` 属于真实采集时间域。字段必须保留明确的时间域说明。

## 临时导出

在任务 6 建立正式 Event Timeline Schema 前，任务 3 的验证导出至少应避免继续使用含糊的 `actual_s`：

```text
event_id,planned_script_s,observed_session_s,skip_session_s,status,event
```

还应导出暂停/恢复记录或足以复算脚本时间映射的数据。空的 `observed_session_s` 必须保持为空，不得回填计划时间或脚本时间。

该 CSV 只用于任务 3 的语义验证，不替代任务 6 的正式结构化 Timeline。

## 测试方法

1. 正常运行时，两条时钟以相同速率增长。
2. 进入 `paused` 后，`session_elapsed_time` 继续增长，`script_elapsed_time` 停止。
3. 恢复后，脚本从暂停位置继续，不跳过暂停期间尚未到达的节点。
4. 多次暂停和恢复后，脚本时间等于真实时间减去累计暂停时长。
5. 前后台切换不重置任何时钟或已记录时间。
6. 事件可以在原计划提示前记录为 `completed`。
7. 推迟的事件保持 `pending`，并可在稍后以当时的真实采集时间完成。
8. 跳过事件保存 `skip_time`，且 `observed_time` 为空。
9. 未进行人工记录的事件保持 `pending` 和空 `observed_time`，不阻止后续采集。
10. 所有 `observed_time`、`skip_time`、`pause_time` 和 `resume_time` 都来自连续真实采集时钟。
11. 导出后能够根据暂停区间复原脚本时间与真实采集时间的映射。
12. 既有任务 2 的后台计时、播报和时间连续性测试继续通过。

## 设计边界

本任务不实现照片、备注、多 Session、进程终止后的完整恢复、Raw ASC 操作或任务 6 的正式 Event Timeline Schema。这些能力继续留在后续任务。

暂停控制因双时钟模型而成为任务 3 的必要组成，但暂停不得改变任务 2 已建立的真实采集时间连续性。

## 待人工审核项

1. 会话使用 `preparing / running / paused / completed / aborted` 是否准确。
2. 事件继续使用 `pending / completed / skipped`，并将 `pending` 定义为非阻塞、非强制确认状态，是否准确。
3. 单个事件推迟时默认只保持 `pending`；是否还需要独立的显式 `deferred`。
4. 任务 3 的临时 CSV 字段和暂停/恢复记录方式是否足以支持后续验证。
5. UI 如何在不要求驾驶员频繁操作的前提下，安全选择提前、推迟或跳过的事件。

## 设计结论

任务 3 应在现有前台服务架构上建立两条严格分离的时钟：真实采集时钟永远连续，脚本执行时钟允许暂停。所有真实操作、暂停、恢复和跳过都以真实采集时钟记录；脚本只提供可暂停、可偏离的执行剧本，不得覆盖现场事实。
