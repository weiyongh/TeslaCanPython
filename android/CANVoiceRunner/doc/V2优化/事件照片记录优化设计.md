# 事件照片记录优化设计

## 1. 任务范围

任务 4 在既有采集会话中增加照片证据采集，使每张成功保存的照片都能追溯到当前采集 Event 及其真实拍摄时间。

本任务只设计照片采集、绑定、保存、查看和照片备注入口，不实现任务 5 的备注数据、不展开任务 6 的录音设计、不定义任务 7 的最终 Timeline 导出结构，也不承担任务 8 的进程终止恢复。

## 2. 事件绑定

1. 一个 Event 可以关联零张或多张照片。
2. 用户点击“拍照”时，App 立即冻结当时主界面对应的 Event 绑定上下文；即使相机界面打开期间脚本继续推进，照片仍绑定点击时的 Event。
3. 绑定信息至少保留：
   - `event_sequence`：Event 在脚本中的顺序；
   - `event_id`：如 `E05`；
   - `event_action`：脚本原始实验目标动作，不因文件名清洗而改变；
   - `photo_sequence`：该 Event 内成功照片的顺序；
   - `photo_id`：如 `E05-P01`。
4. 只有照片成功保存后才正式生成照片记录、占用顺序号并增加照片数量。拍摄或保存失败不生成记录、不占号。

## 3. 文件名与存储

建议文件名：

```text
E05-P01_充电开始_20260909_153025_827.jpg
```

组成依次为 `photo_id`、经过文件名安全清洗的事件名称、真实拍摄 Clock 时间戳。文件名只用于人工辨认和进程终止后的辅助找回，不作为唯一关系数据库；原始 `event_action` 必须单独保留。

任务 4 早期设计曾建议保存到：

```text
Pictures/CANVoiceRunner/<Session>/
```

任务 8 后续审核的统一 Session 目录覆盖上述早期路径。实际实现保存到：

```text
Download/CANVoiceRunner/<Session>/photos/
```

照片记录保存 `content_uri` 与 `file_name`，不依赖可能失效的绝对文件路径。

## 4. 拍摄时间合同

一张照片记录同一物理拍摄时刻的两个时间坐标：

```ini
captured_clock = 2026-09-09T15:30:25.827+08:00
captured_script_time_us = 84827361
```

- `captured_clock`：真实拍摄时刻对应的现实 Clock，包含日期、毫秒和时区。
- `captured_script_time_us`：从本次采集 `script_time` 零点到真实拍摄时刻的单调时间偏移，单位为整数微秒；暂停播报时仍继续增长。
- 公开数据合同不增加 `captured_clock_epoch_ms`，避免与可读 Clock 字段重复。内部映射如需 Epoch 数值，可由 `captured_clock` 计算。
- 可选审计字段 `capture_requested_script_time_us` 只记录用户按下拍照按钮的时刻，不得替代真实拍摄时间。

真实拍摄时刻应采用图像传感器/图像帧时间戳，不得使用进入相机页面时间、按钮时间、保存完成时间、文件修改时间或 `plan_time` 冒充。

## 5. 拍摄技术方案

1. 使用 App 内嵌 CameraX，不调用外部系统相机，不直接以 Camera2 构建完整相机界面。
2. 默认只使用后置主摄，采用单张顺序拍摄、自动对焦和自动曝光；不增加前后摄切换、滤镜、连拍或专业参数。
3. 通过 `ImageCapture.takePicture` 获取内存中的 `ImageProxy`，读取 `ImageInfo.getTimestamp()`，确定真实拍摄时间后再生成正式文件名并保存。
4. 从发起拍摄到保存结果返回期间，拍照按钮不可重复触发。
5. 运行时核验所选相机的传感器时间戳源。目标手机当前报告为 `REALTIME`，可与 `SystemClock.elapsedRealtimeNanos()` 建立同源映射：

```text
captured_script_time_us =
    (image_timestamp_ns - session_start_elapsed_realtime_ns) / 1000
```

6. `captured_clock` 通过邻近采样的墙上时钟（wall clock）与单调时钟锚点映射得到。绝对 Clock 记录到毫秒，不伪造微秒级现实钟表精度。
7. 若运行时发现相机时间戳不是 `REALTIME`，或时间戳无效、倒退、超出拍摄请求与回调的合理边界，不得声称已获得准确映射；本次拍摄按失败处理或明确标记时间不可用，具体实现采用失败优先策略。

## 6. UI 与操作

### 6.1 主界面

- 保留已审核的统一主界面，不改变既有中央采集执行区布局与外观。
- “拍照”按钮在采集中和播报暂停中可用；未开始、准备倒计时和采集结束后置灰且不可点击。
- 证据摘要中的 `照片 N` 显示当前 Session 成功保存的照片总数，也是查看入口；`照片 0` 置灰且不可点击。
- 照片保存成功后才更新 `N`。

### 6.2 照片列表

点击 `照片 N` 进入当前 Session 的照片列表：

- 按 Event 分组；同组内按 `captured_script_time_us` 正序排列；
- 显示缩略图、`photo_id`、Event 名称、拍摄 Clock 和“耗时”；
- 文件被外部删除或不可读取时显示“照片不可用”，不得崩溃，也不得静默删除原有时间与事件关系；
- 预留“添加备注/修改备注”入口和单行备注摘要，由任务 5 实现；拍照成功后不强制弹出备注框。

### 6.3 全屏预览

点击缩略图进入全屏预览。预览页只显示图片和右上角关闭按钮，不增加元数据、左右滑动、编辑、删除、分享或缩放。

进入相机、照片列表、全屏预览或后续备注对话框时，不得隐式暂停 `script_time`、脚本计划进度或 TTS 调度。

## 7. 异常与边界

1. 权限被拒绝、相机不可用、拍摄失败、保存失败或存储空间不足：只显示简洁失败提示，不生成照片记录、不占编号、不增加数量。
2. App 进程终止视为本次采集失败，任务 4 不恢复照片与 Event 的内存关系；终止前已经成功写入 `MediaStore` 的图片允许保留，不自动删除。
3. 终止后保留的图片仍可凭 Session 目录和可读文件名人工识别，但这不等于任务 8 的可靠恢复。
4. 多 Session 相册、跨会话检索、照片清理和恢复机制不属于本任务。

## 8. 实现验收要点

1. 同一 Event 连拍两张成功照片，生成连续且不重复的 `E05-P01`、`E05-P02`，两张均绑定 `E05`。
2. 点击拍照后脚本推进到下一 Event，照片仍绑定点击时被冻结的 Event。
3. 暂停播报期间拍照，`captured_script_time_us` 仍按真实时间增长。
4. `ImageInfo` 时间戳到 `script_time` 的换算在真机上非零、单调，并落在拍摄请求与结果回调的合理时间边界内。
5. 拍摄或保存失败不生成照片记录、不占号、不增加主界面照片数量。
6. 外部删除图片后列表显示“照片不可用”，关系元数据仍保留。
7. 照片列表、预览和相机操作不暂停脚本或 TTS。
